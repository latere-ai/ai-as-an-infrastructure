第八部分 · 安全、可解释性与治理 · 第 36 章

运行时安全：护栏与内容审核

作者
Changkun Ou
更新于
2026 年 6 月 21 日
阅读时长
约 8 分钟

第 10 章 里的对齐塑造了模型倾向于说什么，第 35 章 里的授权约束了智能体被允许做什么。在两者之间，还夹着一层谁都没有覆盖的东西：在服务的那一刻、在真正进出的文本上所执行的策略边界。读完这一章，读者能够解释一个在训练中已经对齐的模型，为何在推理时仍然需要一道独立的守卫；能说出纵深防御栈由哪些部件组成、每一件各自落在什么位置；能掂量每次请求多跑一个模型在延迟和金钱上的代价；也能讲清楚为什么一道护栏是必要的，却又从来不是充分的。

一个已对齐的模型为何仍需要边界

训练时的对齐产出的是一个带有性情的模型：它倾向于拒绝那些偏好数据教它拒绝的请求。这种性情被烤进了权重，而权重是整个栈里改起来最慢的东西。一个做服务的运营方，面对的是三股比一次训练运行更快的压力。

策略变得比权重更快。一个平台周一发现了一种新的滥用模式，它没法在周二之前把一个前沿模型重新训练并重新评测一遍，但它可以在一个小时内给模型前面的分类器加一条规则。一个模型服务于许多套策略。同一份权重，既回答一个儿童教育产品，也回答一个内部的安全研究工具，而允许与拒绝之间的那条线，对两者并不相同，所以它不可能住在两者共享的那份权重里。而且边界必须可审计。运营方得向监管者或客户精确地展示拦下了什么、为什么拦，这意味着这个判断必须由一个会吐出可记录裁决的部件做出，而不是由弥散在数十亿参数里的某种性情做出。

应对之道，是把生成器包在一个独立的分类器（一个守卫模型）里：在生成器看到输入之前先筛输入，在用户看到输出之前先筛输出。守卫模型小、便宜、可替换，并且产出一个离散、可记入日志的标签。它不取代对齐；它只是把那部分必须按运营的节奏、而非按预训练的节奏来移动的策略，外置了出来。

这个栈：纵深防御

没有任何单一部件能独自扛起整道边界。一个生产系统把廉价、宽泛的过滤器摆在昂贵、精确的过滤器前面，于是常见情形被早早挡下，只有含糊的情形才抵达那个昂贵的裁判。从请求往里、按顺序读这些层，是看清每一层各为何而设的最清楚的办法。

系统提示是最廉价、也最薄弱的边界：它用自然语言把策略写在模型自己的上下文里，而在那里它要和模型读到的每一条别的指令竞争，包括那些怀有敌意的指令。规则过滤器是确定性的，也快：一张黑名单，一条匹配违禁模式的正则，一个在邮箱地址或信用卡号抵达模型之前就把它抹掉的检测器。它们几乎不花算力就拦住显而易见的情形，却漏掉一切需要理解的东西。守卫模型是理解登场的地方：一个分类器，读输入、或读输出，对照一套策略分类法给它打标签。网关，也就是 第 24 章 里那个已经为预算与路由坐在每个请求上的部件，是执行裁决、写下审计记录的天然位置。

演化：从黑名单，到守卫模型，到可编程护轨

最早的内容边界是一张违禁字符串的清单，它的失效方式众所周知：它拦的是词而不是意思，所以靠改拼写就能轻易绕过，对无辜文本又轻易地过度拦截。越过它的第一个上规模的步骤，是一个专门的内容审核分类器，针对一套不良内容分类法训练，作为一个开发者在每条消息上调用的端点暴露出来，并且是刻意为应对真实世界的流量、而非一个干净的基准而造的 (Markov et al. 2022)。它把边界从字符串匹配挪到了学到的类别，但它依然是一个固定的、由厂商定义的分类器。

另一条路线试图把边界挪回模型里。Constitutional AI 训练模型对照一套写下来的原则去批评并修订自己的回答，从而让更多的拒绝行为是内部的，让模型能解释自己的反对 (Bai et al. 2022)。这磨利了那种性情，也减少了外部守卫需要接住的量，但它并不消除对守卫的需要：一个固定的性情，依然追不上一套在权重冻结之后才变动的策略。

如今的形态，是开放、可微调的守卫模型。Llama Guard 是一个建在语言模型之上、对照一套显式安全分类法训练的输入输出防护，于是运营方可以同时对提示和回答做分类，而且关键在于，可以把分类法适配到本地策略上 (Inan et al. 2023)。ShieldGemma 把同一个想法扩展到一系列模型尺寸，并给出经过校准的类别预测，让守卫在小尺寸端便宜到足以在每个请求上跑，在大尺寸端又准到足以信任 (Zeng et al. 2024)。在分类器之外，可编程护轨框架让运营方为模型周围的控制流写脚本，把允许的话题与对话路径定义在一份配置里、而非定义在权重里 (Rebedea et al. 2023)。三者合在一起，就是现代的栈：一份来自训练的性情，一个管策略的分类器，一条管控制流的护轨。

权衡：第二意见的代价

守卫模型是第二个模型，跑它就有第二个模型的代价。筛输入，在生成开始之前加了一次前向。筛输出，在生成结束之后加了一次前向。在最朴素的实现里，一个被守卫的请求因此要为两次额外的模型调用付费，而被守卫的模型相对守卫越小，这份开销占的比例就越显眼。金钱上的代价，是同一个故事经 第 42 章 读出来的版本：每一个被守卫的 token 如今都记在两个模型的账上，到了规模上，守卫那一份账并不可忽略。

约束箭头

输出守卫想拿到整个回答才能判它，但 第 16 章 的服务栈把 token 流式地吐出去以削减首字时延，而一个已经读到一句有害话的用户，没法把它读回去。这道边界逼出一个一直伸到服务 SLA 里的选择。把回答缓冲下来整段审核，你就把流式省下的延迟原数还回去。在 token 流出时分块审核，你能把一次生成拦腰截断，却削弱了判断，因为一段话在它后面那段出现之前都显得无害。所以安全策略同时也是一个延迟预算的决定：守卫相对于这条流坐在哪里，既定了产品有多安全，也定了它感觉上有多快。

另一重权衡，是分类器自己的错误面。一个调到一点都不漏的守卫，会拒绝得太多，而过度拒绝是一项真实的代价、不是一个安全的默认：一个编程助手因为 kill -9 里出现了 "kill" 就拦掉这个词，它辜负用户的程度，和一个泄露内容的守卫一样确凿。一个调到很少拒绝的守卫，会放过更多。落在那条曲线上的工作点是一个产品决定，而且逐策略而异，这恰恰就是边界为何住在共享权重之外的原因。

而守卫是有孔的。一个读文本的分类器，能通过它所读的文本被攻击：一个精心构造得在守卫看来无害、在生成器看来恶意的输入，溜过了输入筛；一个编码得在守卫看来无害的输出，溜过了输出筛。对这些攻击的系统研究是 第 37 章；这里要点是架构性的。一道护栏抬高了常见滥用的成本，并产出审计记录，这两件事它都是必要的。它不是充分的，因为一个铁了心的对手会把它当作又一个要骗过的模型，而上面那一层，也就是 第 34 章 里的监督与控制，存在的理由恰恰是：没有任何单一的过滤器守得住。

实现：一个被守卫的请求

一个被守卫的请求，最小的形态是包住生成的三个步骤，并且把流式那一步的决定摆到明面上。

def guarded_generate(request, policy):
    # 1. Cheap deterministic filters first: reject the obvious, redact PII.
    request = redact_pii(request)
    if rule_filter(request, policy):
        return safe_refusal(policy)

    # 2. Input guard: one classifier pass before the generator runs.
    if guard_model(request, policy, side="input").unsafe:
        return safe_refusal(policy)

    # 3. Generate, moderating the stream in bounded chunks so a violation
    #    can stop the response before the user reads past it.
    buffer = []
    for chunk in generator.stream(request):
        buffer.append(chunk)
        if len(buffer) >= CHUNK and guard_model(
            "".join(buffer), policy, side="output"
        ).unsafe:
            return safe_refusal(policy)  # cut the stream
        yield chunk

守卫据以分类的那套分类法、分块的大小、以及在拒绝与安全补全之间的取舍，全都是配置、不是代码，因为这三者都是策略，而策略正是那个必须不靠重新部署就能移动的东西。

什么仍有争议
  • 在模型内对齐，还是用一个外部分类器？ 一派主张边界属于权重，在那里模型能对意图做推理、能解释自己的拒绝 (Bai et al. 2022)；另一派主张一个固定的性情追不上一套移动的策略，边界必须是一个外部的、可替换的部件 (Inan et al. 2023)。实践中两者都在出货，悬而未决的问题是如何分工。
  • 基于规则，还是基于模型的护轨？ 确定性过滤器可审计、快，但脆；基于模型的守卫懂意思，但自己也可被攻击，还多加一次前向。两者的配比没有定论，且因产品而异。
  • 对流式输出做审核，到底成不成立？ 判一个不完整的回答，就是判一个不完整的对象，而一个无害的前缀，可能在下一个 token 就转为有害。分块审核究竟是真安全、还是一个令人宽心的近似，是真有争论的。

把运行时安全读一遍

能力、效率、信任这面镜子，把这一层读成几乎纯粹的信任，用效率来付账。守卫不添能力；前面摆一个分类器，模型并不更能干。它直接耗效率：每个请求多一个模型，外加一笔压在流式延迟上的税，而那延迟正是 第 16 章 费力去削减的。它换来的，是一种特定的、运营意义上的信任：一道按运营节奏变动、逐租户而异、并吐出一份运营方敢于背书的审计记录的策略边界。这就是这一层为何住在它所守卫的权重之外，也是它为何必要、却从来不是答案的全部。
