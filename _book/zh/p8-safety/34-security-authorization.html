第八部分 · 安全、可解释性与治理 · 第 34 章

安全与授权

智能体代表某个人在世界里做事，每次行动都带着权限。核心的安全问题很简单：每次调用带多少权限、能带多久。最坏的情况是这样：一个权限太大、存活太久的令牌，加上一次提示注入，就等于一次数据泄露。身份和治理两个系统各司其职，一个决定权限有多大、一个确保网络上真的按那个大小来。预算和审计到最后还是依赖一个经过验证的调用者身份。

命名问题的那次入侵

2025 年 5 月，Invariant Labs 披露了 GitHub MCP 的一个漏洞 (Labs 2025)。场景很简单：一个个人访问令牌，权限很大，涵盖用户的所有仓库，在整个会话里反复用。攻击者在公开的 issue 里塞了个恶意指令。智能体读到那个 issue 时照着指令做了，因为手里那个令牌权限足够大，结果就把私有仓库的内容外泄了。这里的失败不是密钥泄露，而是一个本来应该被正确保管的密钥权限太大、活得太久。

这个例子浓缩了全章的问题。智能体要做的事都需要权限：读仓库、发邮件、查数据库、调模型。最方便的办法是签发一个大权限令牌给智能体，整个会话都用它。麻烦是：这个长期的授权任何能接触智能体的东西都能用。而智能体本来就要读不信任的内容，攻击者可以在网页、文件、工具返回里埋指令，迫使智能体用那个令牌做坏事。令牌无法分辨这次调用是智能体的真实意愿还是被糊弄了。

攻击面就是那个权限列表。一个大权限、长生命周期的令牌一旦被注入的指令拿到，就能干那个令牌能干的所有事（图 34.1）。爆炸半径不是攻击者进去那一个仓库，而是这个令牌覆盖的所有仓库。

这只是更大问题的一个例子。还有三个叠加的风险。第一，智能体跑在共享基础设施上，平台得知道每次操作来自哪个租户，否则一个查询就能悄悄把这个租户的数据漏进另一个租户的会话。第二，付钱用模型、授权这些操作的 API 密钥和 OAuth 令牌，绝对不能让可能泄露它们的代码看到。第三，用户撤销同意时，已经签出去的权限必须真的失效，不能只是标记一下。这三个问题问的都是同一件事，只是对象不同：有多少权限跟着这次调用，存活多久。

两个系统，一个问题

答案是把权限变成一个明确、小范围、短期、来源清楚的东西。在成熟的平台上，两个系统分工处理这个问题，同一个问题它们各自负责一部分：治理说明智能体允许干什么，身份在网络上确保真的就是这样。这两个系统一起工作之前，都依赖同一个基础。

主体元组

每个操作都把调用者分解到这个元组里： (user_id, tenant_id, agent_id, workload_id, scopes, attributes)。这个元组回答一个问题：这个调用者能不能在这个资源上做这个动作。其他所有系统都用这个。数据库层把它绑到会话上，成本系统用它计费，审计日志用它追溯。一条只说「会话 X 做了 Y」的日志，如果没有这个经过验证的元组，调查时最关键的两个问题——谁干的、哪个租户——根本答不了。

三个身份，互不相关

每次调用时运行框架要校对三个身份，它们是独立的轴，没法合并（图 34.2）。

用户是通过 SSO 认证的真人，同意能被撤销。智能体是命名的、有版本的、有自己能力集合的东西，正因为它独立存在，才能说「是智能体干的，不是用户」。工作负载是运行时，它要回答另外两个答不了的问题：这真的是合法的框架进程，还是集群里其他什么东西偷了令牌。每个身份堵住别的两个留下的一个漏洞，也各自承载别的两个承载不了的追溯属性。

声明与执行

两个系统分工，接缝处是本章的核心。治理声明规则：这个智能体只能读、只能读这个仓库、花费不超过多少。身份执行这个规则，办法是生成一个严格按这个范围来的令牌，任何更宽的都拒绝。能力限制是治理说的话，令牌的 scope 是身份把这个话变成网络上的现实。最清楚的分法是问：撤销它会改变什么。改变谁能访问某个资源，那是身份的事；改变已授权的人能尝试什么，那是治理的事。令牌的 scope 声明就在这条缝上，身份在这里把治理的决定编进去（图 34.3）。

治理把智能体当成一份文档，不是运行中的进程：有名字、所有者签过、有版本的记录，包含提示、工具清单、绑定的模型、预算、审批步骤。文档能回答「这个智能体在行动那一刻被允许干什么」，因为权限就是版本控制那一时刻的那个版本。委派有个核心约束：Cchild⊆CparentC_{child} \subseteq C_{parent}Cchild​⊆Cparent​。工作沿链往下传时，权限只能缩小，不能长大。

凭证保管

提供商密钥和 OAuth 令牌住在系统里，绝对不能在智能体的环境、配置、日志、命令历史里显现。智能体得到的是个有范围、短期的句柄，系统在调用时才换成真凭证。这跟框架在沙箱边界上的规则一样（第 23 章）：生成的代码看不到高价值密钥。提供商密钥尤其要保护，因为一旦泄露，爆炸半径是别人账户上的花费，直到账单来才能发现。

租户作为最粗的所有权轴

每个资源要么明确标着租户，要么默认属于某个租户。隔离粒度有个谱，从逻辑到物理。选哪个看 bug 出现时爆炸半径有多大。这要按资源类型逐个选，不能平台统一，因为风险不同：少一行审计记录是隐私问题，但跨租户的记忆检索泄漏是真正的数据泄露，会把一个租户的东西漏进另一个租户的活会话（第 22 章、第 25 章）。

从宽大到短暂

为调用签发权限的方式一直在演进，从宽且持久往小且短期走，每个变化都是某个事件教出来的。GitHub 的入侵在这条线的起点，不是终点：智能体面对不信任的输入时，最早的那套办法就是这样。

大权限、长生命周期令牌最初就是标配，因为只需一次同意、一个凭证。代价是：这样的令牌是长期授权，任何能接触智能体的东西都能用。GitHub 的细粒度个人令牌、Google 的限权同意框，都是为了从这个模式里夺回点控制权。

短期能力令牌反过来：每次工具调用生成一个只有这次调用需要的权限的令牌，TTL 以分钟计。这样一旦泄露或被注入，伤害窗口从整个会话缩到一次操作。Macaroons（2014）和 Biscuit 是理论基础：令牌持有者可以限制令牌，加的条件只会进一步收紧、不会放宽，服务可以把一个更弱的令牌传给下一跳，不用回头问签发者 (Birgisson et al. 2014)。这就是对象能力纪律，在令牌层就是 Cchild⊆CparentC_{child} \subseteq C_{parent}Cchild​⊆Cparent​。

**代表用户（OBO）**让用户的权限一直往下传，不是被智能体的权限替换掉，这样数据库的行级安全看到的是真人，不是服务账号。RFC 8693 标准化了令牌交换 (Jones et al. 2020)。针对智能体的答案是 IETF 的 draft-oauth-ai-agents-on-behalf-of-user-00，把用户、智能体、客户端身份打进一个委派令牌 (Group 2025)。Okta for AI Agents (Okta 2025) 和 Auth0 的智能体身份 (Auth0 2026) 都上线了。

工作负载身份（SPIFFE/SPIRE）让 pod 用密码学证明自己，没有可泄露的共享密钥。这样令牌系统就能拒绝给集群里某个随便拿到的进程签用户令牌，多副本部署的必配。

这段历史的选择规则：大权限只在单用户、低权限部署站得住；高权限或不可撤销的操作值得用能力令牌；下游要看真实用户身份就得用 OBO；多副本部署必须用 SPIFFE。

争议所在治理是否需要独立于身份的系统，还没有定论。怀疑派说：身份已经能签发可限制、有范围、能委派的令牌（Macaroons、Biscuit、OBO，还有元组里的 `agent_id`），没必要再单独要一个系统。支持分离的人指出：身份自己答不了这个问题——这个智能体在行动时被允许干什么。不是令牌范围，而是它的提示、工具清单、预算、批准步骤，就是那份版本化的智能体文档，身份管不了。但对方说得对：这个市场太小了，还没有成熟的、不绑定厂商的「治理系统」品类，身份领域有 Okta、Auth0、SPIFFE，治理领域没有。市场小可能意味着是个被忽视的原语，也可能意味着根本不是原语。所以这个问题还悬着。

权衡陡峭的地方

每个选择都在两个好处之间权衡，而且转折点都很陡。五个权衡反复出现，每个都看起来合理，但各有对立方案没有的尖锐坏处。

  • 隔离粒度与共享灵活性。 单用户租户隔离很简单但没法共享。三层的组织项目体系清晰，遇上矩阵组织就崩。属性式访问适应任何拓扑，但「谁能看什么」无法从数据里直读，离线审计和数据清理就没法遍历。找最简单的、既合适又能遍历的结构。
  • 撤销延迟与长 TTL。 持有令牌的撤销延迟避不了：用户撤销同意，已签的令牌还活着，会话继续用那个权限直到过期。TTL 就是被撤销权限的生存上限。长 TTL 和立即撤销没法同时要，租户越关键令牌活得越短。
  • 写时分区与读时过滤。 读时加 tenant_id 过滤只差一个漏掉的 WHERE 就泄露；物理分区的索引即便查询错也泄不出。过滤便宜，分区更安全。
  • 同意疲劳。 每个操作都弹同意框，用户最后会给最大权限来关闭对话，正好制造环境授权。真正的修复是把智能体当独立身份，有自己长期、可审计的权限，不是每次都跟用户再借。
  • 集中化与可用性。 在所有调用前放统一系统，追溯和实时预算才可能，但这本身是单点故障：一宕机所有会话停。这份控制要用备用路由和熔断器来补偿。

下面拖动 TTL 滑块，能看到被撤销的令牌还有多久能用：假设同意在令牌生命周期内随机某个时刻被撤回，平均暴露窗口是 TTL 的一半，最坏情况是整个 TTL。

import numpy as np

rng = np.random.default_rng(0)
trials = 100_000
for ttl_min in [60, 15, 5, 1]:
    # consent withdrawn at a uniformly random moment within the token's life
    withdraw = rng.uniform(0, ttl_min, trials)
    # exposure = time the session keeps running on revoked authority
    exposure = ttl_min - withdraw
    print(f"TTL={ttl_min:>3} min  ->  mean exposure {exposure.mean():5.2f} min,"
          f"  worst case {exposure.max():5.2f} min")
print("\nExposure window scales linearly with TTL: the TTL is the ceiling.")
约束箭头预算控制由身份决定，不是成本系统。「这个租户一个月五千美元上限」要真的管用，每次模型调用得在调用那一刻、花钱之前就带上**经过验证的**租户信息（@sec-economics）。失控花费事件，比如 47,000 美元的智能体循环 [@waxell2025loop] 和五小时烧掉 16.7 亿词元的 Claude Code 递归 [@claudecode2025tokens]，都不是纯成本系统问题。两个事件都设过预算，问题是系统只能在花完了才知道谁花的。租户级预算控制必须建在已验证的调用者身份上，因为追溯得先于调用发生，而成本上限的精度取决于身份有多精确。

回答那个问题的组件

策略引擎真正回答「这个调用者能不能对这个资源做这个操作」。OPA/Rego 是 Kubernetes 原生、数据驱动，学习曲线陡。AWS Cedar 是有类型、可分析的，能问形式化问题（「某个主体有没有可能访问这个资源」），不只是测试。Oso 是库形式授权，有关系模型；Permit.io 组合这些后端。生产通常跑两套策略：身份侧是资源访问（「这个身份能不能读这个资源」），治理侧是操作风险（「这个智能体能不能发这封邮件」），因为变化的原因和频率不同，人工审批也是在后者（第 33 章）。

隔离层级

按资源类选隔离层级：

层级 机制 缺陷时的爆炸半径 适用
逻辑 共享库加租户列加强制过滤 漏一个 WHERE 全泄 开发、内部工具、低风险 SaaS
命名空间 每租户独立 schema 或命名空间 路由错的查询打到错的租户 多数 B2B SaaS
物理 每租户独立库、集群或账户 缺陷关在一个租户里 受管制、大企业、主权云

成熟平台混用这几层：会话为成本用逻辑分区，敏感记忆用物理隔离，审计日志是带租户标签的共享物理存储。下面的坑：租户身份来自请求头。如果 tenant_id 从无密码学保证的 HTTP 头读（不是 JWT 声明也不是 mTLS 证书），一个假头就能在门外绕过你精心选的物理隔离。

闭合回路

两个运维模式把流程闭合。预算控制得和调用同步，在模型访问系统或网关里，那是唯一既看得到每次调用又有权拒绝的地方；计费系统来控制预算只能告警，因为它是在花完了才知道。清除权和审计的记录保留要求有张力，用墓碑加证明来解决：删数据载荷，保护防篡改链，用证明记录删除，别悄声丢行。

反复出现的失效都是身份边界没画清楚。环境授权就是 GitHub MCP：一个长期令牌，每次都用，提示注入来了就能用这个令牌的全部权限。智能体转发用户令牌给另一个智能体，下一个就拿到了用户全权，但没有用户意图；正确做法是委派、收窄的令牌，标明整条链，每跳进一步收窄，搞砸委派是多智能体系统失效的主因 (Cemri et al. 2025)（第 24 章）。跨租户记忆检索泄漏最危险，得靠写时分区不是读时过滤。隐式租户耦合，资源创建时隐式继承租户身份，导致无法共享、无法重新分配，除非数据迁移，可隐式租户身份表达不了这种迁移。
