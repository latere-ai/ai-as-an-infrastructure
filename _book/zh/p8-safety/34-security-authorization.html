安全与授权

智能体代表某个人在世界里做事，每次行动都带着这个人的权限。于是核心的安全问题就是：每次调用带走多少权限，又带多久。一个权限太大、活得太久的令牌，再加上一次提示注入，就等于一次数据泄露。要看清这一点，得先弄明白身份和治理如何分工，一个划定权限有多大，一个在网络上把这个边界落实。也要看清预算和审计为什么到头来都依赖一个经过验证的调用者，而不是各自独立的系统。

命名问题的那次入侵

2025 年 5 月，Invariant Labs 披露了一种把合理配置变成跨仓库数据泄露的干净手法 (Labs 2025)。GitHub 的 MCP 集成走的是常见路子：一个个人访问令牌，权限大到能覆盖用户的所有仓库，整个会话期间反复使用。攻击者在一个公开 issue 里埋了指令。智能体读到这个 issue，就照着指令做了，而手里那个令牌本就覆盖了用户的私有仓库，于是智能体用它把私有内容外泄了出去。失败的不是泄露的密钥，而是一个被正确保管、却权限太大、活得太久的密钥。

这句话浓缩了整章，值得拆开来看。智能体存在的意义就是做事：读仓库、发邮件、查数据仓库、调模型。每个动作都需要权限，而最省事的默认做法，是一次性给智能体一个大权限凭证，让它在整个会话里反复用。问题在于，这种长期授权，任何能够接触智能体的东西都够得着，而智能体的输入通道天生是敞开的：它读的就是不受信任的内容。攻击者只要在网页、文件、或某个工具的输出里埋下指令（这属于间接提示注入，工具投毒是其中一种），就能引导智能体动用这份授权。令牌分辨不出，这次动作是智能体自己决定的，还是被骗的。

所以攻击面就是那张范围清单。权限既大又长寿，一条被注入的指令就能放大成这个凭证允许的一切（图 34.1）。爆炸半径不是攻击者够到的那一个仓库，而是同一个令牌覆盖的每一个仓库。

GitHub 这一例只是某种更普遍失败的一个形态，另有三个问题与它叠加。智能体跑在共享基础设施上，平台必须知道每个动作属于哪个租户，否则一次检索就会悄悄把一个租户的数据带进另一个租户的会话。付钱用模型、并为这些操作授权的提供商密钥和 OAuth 令牌，绝不能让那些可能泄露它们的生成代码够得着。还有，当人撤回同意时，已经签发出去的权限必须真的停下来，而不只是被打个标记。这三件事问的是同一个问题，只是换了对象：有多少权限跟着走，又跟多久。

两个底座，一个动作

答案是把权限做成一等的、窄的、短命的、有归属的东西。在成熟的平台里，这样东西由两个相互配合的底座共同拥有，它们把同一个动作劈成两半：治理声明智能体可以尝试什么，身份在网络上执行它。到达这条接缝之前，两个底座都先消费同一个基础构件。

主体元组

每个操作都把它的调用者解析成 (user_id, tenant_id, agent_id, workload_id, scopes, attributes)，并回答一个问题：这个主体能否在这个资源上做这个动作。这个元组是其他所有系统消费的东西。持久化把它盖在会话上，成本流水按它计费，审计日志归属到它。一条只记录「会话 X 做了 Y」、却没有这个经过验证的元组的审计项，答不了调查唯一关心的两个问题：是谁，又是哪个租户。

三个身份，不是层级

每次调用，运行框架都要校对三个主体，它们是无法压扁成一个的正交轴（图 34.2）。

用户是通过 SSO 认证的真人，其同意可以撤回。智能体是一个有名字、有版本的主体，带着自己的能力面，正因为有它，「是智能体做的，不是用户」这句话才说得出口。工作负载是运行时，它回答另外两者答不了的问题：这究竟是一个合法的框架副本，还是集群里某个搞到了令牌的别的东西。每个身份都堵住另外两个留下的一个攻击口，也各自承载另外两个承载不了的归属。

声明与执行

两个底座分担划定权限的工作，而它们之间的接缝，是本章承重的那个想法。治理声明一项收窄：这个智能体只能读、只能读这个仓库、只能在某个花费上限之下。身份执行它，办法是铸造一个恰好按这个范围来的令牌，并拒绝铸造任何更宽的。能力收窄是治理的词汇，令牌范围是身份把这套词汇落到网络上的机制。判断某项关注归哪个底座，最干净的检验是：撤销它，若改变的是谁能够到某个资源，那是身份；若改变的是一个已授权主体被允许尝试什么，那是治理。令牌的 scope 声明之所以正好坐在接缝上，是因为身份把治理的决定写进了它（图 34.3）。

治理把智能体看成一份文档，而不是一个运行中的进程：一份有名字、由所有者签署、带版本的记录，写明它的提示、工具授予、模型绑定、预算和审批步骤。这份文档才能回答「这个智能体在动手那一刻被允许做什么」，因为它被允许的，就是版本控制里某一点上的那份文档。委派上承重的那条不变量是 Cchild⊆CparentC_{child} \subseteq C_{parent}Cchild​⊆Cparent​：工作沿着一条链往下交，权限只会缩，绝不会涨。

凭证保管

提供商密钥和 OAuth 令牌住在底座里，绝不进智能体的环境、配置、日志或命令历史。智能体拿到的是一个有范围、短命的句柄，底座在调用时才用它换出真正的凭证。这跟框架在沙箱边界上施加的密钥可达性纪律是同一套（第 23 章）：生成的代码不能读到高价值密钥。对提供商密钥尤其要紧，因为它们的爆炸半径是别人模型上一笔无人归属的花费，等账单来了才会发现。

租户作为最粗的所有权轴

每个资源要么带着租户属性，要么就悄悄被困在某一个租户里。隔离落在一道谱上，这道谱的定义性质是出 bug 时的爆炸半径，而且要按资源类别逐个选，不是全平台一刀切，因为爆炸半径并不均匀：泄露一行审计是机密性事件，泄露一次跨租户记忆检索却是正在发生的数据泄露，会把一个租户的内容浮现在另一个租户的活会话里（第 22 章、第 25 章）。

从宽大到短暂

为一次调用打包权限的方式，一直在稳步地从宽且持久走向窄且短命，每一步都是被前一种形态酿成的事故推着走的。GitHub 那次入侵在这条弧线的起点，不是终点：它就是最老那套打包方式，遇上智能体读取不受信任输入时的样子。

大权限承载令牌之所以是默认，是因为它只要一次同意对话、一个凭证。它的代价在时间维度上：一个大权限令牌是长期授权，任何能够接触智能体的东西都够得着。GitHub 的细粒度个人访问令牌、Google 收窄过的同意界面，都是为了从这个模式里夺回控制权。

短期能力令牌反转了长期授权：每次工具调用都铸造一个令牌，只带这次调用所需的权限，TTL 以分钟计，于是一次被泄露或被注入的调用能够造成伤害的窗口，从一整个会话缩到一次操作。Macaroons（2014）和 Biscuit 是它的形式化根基：持有者可以收窄令牌，添加的限定条件只会进一步收紧、绝不放宽，因此一个服务把一个严格更弱的令牌交给下一跳时，不必回头去问签发者 (Birgisson et al. 2014)。这就是对象能力纪律，也正是 Cchild⊆CparentC_{child} \subseteq C_{parent}Cchild​⊆Cparent​ 在令牌层的表达。

**代表用户（OBO）**让用户的权限端到端地往下传，而不是被智能体的权限取代，于是数据仓库的行级安全看到的是真人，而不是服务账号。RFC 8693 把令牌交换形式化了 (Jones et al. 2020)；针对智能体的标准化答案是 IETF 的 draft-oauth-ai-agents-on-behalf-of-user-00，它把用户、智能体、客户端三重身份编进一个委派令牌 (Group 2025)。Okta for AI Agents (Okta 2025) 和 Auth0 的智能体身份工作 (Auth0 2026)，把这件事做成了产品，而不只是草案。

工作负载身份（SPIFFE/SPIRE）让 pod 用密码学证明自己是什么，没有可泄露的共享密钥。正是它让令牌中介可以拒绝给一个只是恰好待在集群里的进程铸造用户令牌，凡是多副本的场景都拿它当标准。

这段历史沉淀下来的选择规则是：大范围只在单用户、低权限的部署里站得住；动作高权限或不可逆时，能力令牌才配得上它那套管线；下游授权依赖具体用户时，OBO 就承重；多副本则一律用 SPIFFE。

争议所在治理是不是一个区别于身份的原语，这事真的还没定论。怀疑的一方认为，身份本来就在签发可收窄、有范围、可委派的令牌（Macaroons、Biscuit、OBO，还有元组里的 `agent_id`），所以并没有剩下什么留给一个单独的底座去拥有。主张分离的一方用一个身份独力答不出的问题来回应：这个智能体在动手那一刻被允许做什么？答案不是某个令牌范围，而是一段提示、一张工具清单、一份预算、一组审批步骤，也就是智能体那份带版本的文档，而这份文档身份从来没拿过。诚实的反向砝码是：市场很薄，并不存在一个成熟、不绑定厂商的「治理底座」品类，像身份领域那样有 Okta、Auth0、SPIFFE，也不像沙箱那样成形。薄市场可能是一个尚未被命名的、供给不足的原语该有的样子，但也可能是一个根本不是原语的东西该有的样子，这正是问题悬而未决的原因。

权衡咬人的地方

本章的每个选择都拿一种好处去换另一种，而拐点都很陡。有五个权衡反复出现，每一个都是这样一处：一个站得住的决定，带着对立方案所没有的尖锐坏处。

  • 隔离粒度与共享灵活性。 扁平用户租户天然隔离，却无法共享。三层的组织项目层级一看就懂，可一旦真实组织是矩阵而非树，它当场就僵化。属性式访问能贴合任何拓扑，却让「谁能看到什么」无法靠读数据判定，离线审计和清除遍历就此断掉。挑那个既贴合组织、又让所有权图可以走通的最简单形状。
  • 撤销延迟与长 TTL。 撤销延迟在承载令牌这里躲不掉：用户撤回同意，并不能伸手进已经签发的令牌里，于是会话会一直用着被撤销的权限跑下去，直到令牌过期。所以 TTL 就是一个被撤销的授权还能被利用多久的上限。长 TTL 令牌和立即撤销的权利互斥，而且租户越敏感，令牌就得活得越短。
  • 写时分区与读时过滤。 在读时套上的 tenant_id 过滤，只差一条漏掉的 WHERE 就泄露；一个物理上按租户分开的索引，哪怕查询写错也泄不出去。过滤便宜，分区安全。
  • 同意疲劳。 每个动作都重新弹一次同意框，会把用户训练成只为关掉对话而授予能拿到的最宽范围，这恰恰制造出整套设计想要消灭的环境授权。结构性的修法，是把智能体做成一等身份，让它有自己长期、可审计的授权，而不是一个每次都向用户重借权限的代理。
  • 集中化与可用性。 把单一底座摆在所有模型推理前面，归属和同步预算执行才有可能，但它天生就是单点故障：一旦它倒下，所有活跃会话同时卡住。这份用来换控制力的集中化，必须用一条降级路由和一个熔断器来偿付。

改改下面的 TTL，看看一个被撤销的令牌还能被利用多久的窗口怎么变：假设同意在令牌生命周期内某个随机时刻被撤回，平均暴露是 TTL 的一半，最坏情况是整个 TTL。

import numpy as np

rng = np.random.default_rng(0)
trials = 100_000
for ttl_min in [60, 15, 5, 1]:
    # consent withdrawn at a uniformly random moment within the token's life
    withdraw = rng.uniform(0, ttl_min, trials)
    # exposure = time the session keeps running on revoked authority
    exposure = ttl_min - withdraw
    print(f"TTL={ttl_min:>3} min  ->  mean exposure {exposure.mean():5.2f} min,"
          f"  worst case {exposure.max():5.2f} min")
print("\nExposure window scales linearly with TTL: the TTL is the ceiling.")
约束箭头预算执行由身份决定，不由成本系统决定。一条写着「这个租户每月可花五千美元」的上限毫无意义，除非每次模型调用都在调用那一刻、花钱之前就带着一个**经过验证的**租户（@sec-economics）。那些失控花费事件，47,000 美元的智能体循环 [@waxell2025loop]，以及五小时烧掉 16.7 亿词元的 Claude Code 递归 [@claudecode2025tokens]，都不纯粹是成本系统的失败。两边都设过预算；它们在花费上触发，可系统只能在钱已经没了之后才把这笔花费归到谁头上。租户级执行之所以建在一个经过验证的主体下游，是因为归属必须先于调用发生，而一条成本上限，只能精确到交给它的那个身份那么精确。

回答那个动作的组件

真正回答「这个调用者能否在这个资源上做这个动作」的组件是策略引擎，它是这个底座最显眼的产物。OPA/Rego 是 Kubernetes 原生、数据驱动的，学习曲线不低。AWS Cedar 有类型、可分析，于是你能对一份策略提形式化的问题（「会不会有任何主体能够到达这个资源」），而不只是去测它。Oso 把授权做成一个带关系模型的库；Permit.io 则把这些后端组合在一个 API 之后。一个生产系统会跑两套策略面，并且应该把它们分开：身份拥有的资源访问策略（「这个身份能不能读这个资源」），和治理拥有的动作风险策略（「这个智能体能不能发这封邮件」），因为它们因不同的原因、按不同的节奏变化，而人工审批放在后者（第 33 章）。

隔离层级

按资源类别选择的隔离层级：

层级 机制 缺陷时的爆炸半径 适用
逻辑 共享库加租户列加强制过滤 漏一个 WHERE 就全泄 开发、内部工具、低风险 SaaS
命名空间 每租户独立 schema 或命名空间 路由错的查询打到错的某一个租户 多数 B2B SaaS
物理 每租户独立库、集群或账户 缺陷关在一个租户里 受管制、大企业、主权云

成熟平台会刻意混用这几层：会话为了成本做逻辑分区，高敏感记忆做物理隔离，审计是带租户标签行的共享物理存储。贯穿这一切之下的陷阱，是从请求头里得来的隐式租户：如果 tenant_id 是从一个没有密码学绑定的 HTTP 头里读出来的（不是 JWT 声明、也不是 mTLS 客户端证书），那么一个伪造的头就能在门口绕过你精心挑选的那个物理层级。

闭合回路

有两个运维模式把回路闭合。预算执行必须和调用同步，住在模型访问底座或网关里，那是唯一既有每次调用的上下文、又有拒绝权力的地方；由计费系统执行的预算只是一条告警，不是执行，因为它在花费之后才触发。清除权与审计「记录必须留存」的要求相冲突，用墓碑加证明来化解：清掉数据载荷，保住防篡改链的完整，并证明这次删除，而不是悄悄丢掉一行。

那些反复出现的失效模式，全是被画得不够精确的身份边界。环境授权就是 GitHub MCP 的形态：一个长寿令牌，每次调用都用，提示注入一来就能触发它允许的任何事。把用户令牌转发出去的智能体到智能体委派，等于把用户的全部权限交给下一个智能体，却不附带用户的任何意图；正确的形态是一个委派、收窄的令牌，它标明整条链，并在每一跳收紧范围，而搞砸的委派是多智能体失效的一大主因 (Cemri et al. 2025)（第 24 章）。跨租户检索渗漏是风险最高的一类，靠写时分区压过读时过滤来缓解。隐式租户耦合，即资源在创建时隐式继承了租户，会变得无法共享、也无法重新归属，除非做一次迁移，而隐式租户恰恰表达不出这种迁移。
