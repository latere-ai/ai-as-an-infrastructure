第十部分 · 实践：搭建 2026 技术栈 · 第 44 章

搭建一套 2026 技术栈

本书开篇就许下一个承诺：一项能力是有生命周期的，从算力一路向上直到一个受治理的行为，各层以特定的顺序相连（第 1 章）。本章正是兑现这个承诺。它是收官之作：一套具体的、端到端的参考架构，把前面各实战章节搭起来的零件接成一个运行中的系统。透过这一章，你能在白板上画出整套技术栈，叫得出每一对相邻层之间的接缝，也能写出把它们黏合在一起的代码。

要避开的陷阱，是把本章当成第七篇全景综述。前面六章已经分别讲过模型（第 38 章）、服务与算力（第 39 章）、训练与微调（第 40 章）、智能体与沙箱（第 41 章）、检索（第 42 章）以及评测（第 43 章）。本章问的不是「产品有哪些」，而是：选好了那些层之后，它们如何组合成一个能运行、能观测、能付费的整体？

截至 2026 年年中这是一份带日期的快照（2026 年 6 月）。具体产品、价格、版本与「最适合」的说法变动很快，2026 年尤其是动荡密集的一年（Promptfoo 归 OpenAI，Langfuse 归 ClickHouse，MCP 规范正值改版中途）。请把下文每一个具名产品与金额都视为带出处的指示性参考，而非永恒事实，在投入前重新核实。优先抓住耐久的部分：契约、接缝，以及架构原型。它们比任何版本号都活得更久。

主旨：三份契约与一条纪律

一套 2026 技术栈能组合起来，并不是各工具的功能达成一致（并没有），而是在三份协议上达成一致。每份协议都是个狭窄而无趣的接口，让你能替换它背后的东西，而无需重写它前面的东西。一旦看清一切都在这三道接缝上交汇，整套架构就一目了然。

  1. 模型调用讲 OpenAI 兼容的 HTTP 形态。 /v1/chat/completions、/v1/responses、/v1/embeddings。到 2026 年，每个服务引擎都暴露这一形态（第 39 章），每个托管前沿 API 都提供或近似于此，每个网关都往这一形态靠。因此一个自托管的 vLLM 模型与一个托管的 Claude 端点可以在同一个名字背后互换。
  2. 工具与智能体流量讲 MCP。 Model Context Protocol 之于工具集成，就如同 OpenAI 形态之于模型调用：一个让一台工具服务器能被每个智能体框架复用的公共接口（第 41 章）。到 2026 年，它已是几乎所有框架下的默认工具层，稳定规范是 2025-11-25，其中的无状态版本正处于验证期。
  3. 遥测讲 OpenTelemetry GenAI span。 gen_ai.* 语义约定是 LLM、检索与智能体 span 的厂商中立格式（第 43 章）。埋点一次，就能接到 Langfuse、Phoenix、Datadog 或 Grafana，无需重新埋点。

把这三份协议系在一起的那一条纪律，是虚拟密钥托管。没有任何应用、智能体、评测套件或沙箱会持有提供商凭据。它们持有的是网关签发的短时效虚拟密钥，受限于一个模型白名单、一份预算与一个限流。轮换提供商密钥或给失控的智能体封顶，这些操作都只需要在服务端做，客户端无需重新部署。同样的思路延伸到算力：密钥存在沙箱之外，作为受限令牌递达智能体，绝不硬编码进去（第 34 章）。

三份协议共同汇聚的那个组件是模型网关，本章就是它的归属地。本书没有单独的网关章节，网关就是那层连接组织，所以它的全景以及本章独有的对比表都在这里。

约束箭头网关是下层经济性影响上层架构的地方。因为每一次模型调用都路由经过同一个地址，前沿模型的每 token 价格（@sec-economics）与自托管服务的每 token 成本（@sec-serving-problem）就变成了一条路由规则，而非一处代码改动。把困难步骤升级到昂贵模型或在负载下回退到廉价模型，这个决定在接缝处做一次，就被上面的每个调用方继承。

网关：本章独有的那张表

模型网关（也叫「LLM gateway」或「AI gateway」）是介于应用代码与众多提供商之间的控制平面。最单薄的描述就是一个反向代理：讲一种 API，向外扇出到多家。它真正的职责是把没人愿意散落在应用代码里的五件事集中起来：统一 API、密钥托管、成本核算、回退与路由、预算与策略。最新的网关把这一角色从纯 token 流量扩展到智能体原生协议（工具用 MCP，智能体间用 A2A），让网关成为整套技术栈流量的单一策略点。

如何选型，取决于两条比功能清单更重要的轴：先看托管 vs 自托管，再看纯 LLM vs 智能体原生。

  • 想要零基础设施、快速访问广阔目录，且能接受提供商密钥与请求元数据经过第三方的，选托管网关（OpenRouter、Cloudflare、Portkey 托管版）。最适合原型与小团队。
  • 提供商密钥必须留在自己的环境里，或需要自己掌握的数据驻留与逐请求审计的，选自托管网关（LiteLLM、agentgateway、Envoy、Bifrost）。最适合受监管行业与平台团队。
  • 路线图需要把 MCP 工具调用与智能体间流量纳入与 token 流量同一个策略点，不想日后再把智能体治理硬塞进一个只懂聊天的代理的，选智能体原生网关（agentgateway）。

关于性能：厂商发布了惊人的延迟数字（「快 50 倍」「亚毫秒开销」），这些数字在不一致的条件下测得，本处未做验证。对几乎所有工作负载，提供商与模型的延迟都以数量级压过网关开销。在让开销成为决胜因素之前，先在自己的流量上做基准。

想掌控自己的密钥与成本，又不愿大举投入平台的团队，明智的默认是自托管 LiteLLM 并配一层可观测性。理由很简单：覆盖最广，而几乎其他一切都与它互通。（作者自己的技术栈用 Lux；它在此作为这些模式的示范案例出现，而非对上述选项的中立优选。）

参考架构

图 44.1 把各实战章节里逐层的接线图合并成一张图。从上到下读是一条请求流；从左到右读是那几份协议。网关是枢纽，一切需要模型、嵌入、重排或裁判调用的都经过它。沙箱是智能体的算力接缝，与网关的模型接缝相对应。检索紧挨着智能体。评测与可观测性接到网关与 span 上。算力与编排层是这一切之上所立足的地板。

有三件事让这张图在生产里立得住，每一件都是主旨里的一份协议：

  • 一个 base URL，OpenAI 形态。 应用、检索器（做嵌入与重排）、评测套件、裁判都指向同一个网关地址。换模型或加回退是配置，不是代码。一个自托管的 bge-m3 嵌入模型与一个托管的 Cohere 重排模型能在同一道接缝后按名字寻址（第 42 章）。
  • 一个工具协议，MCP。 智能体不直拨任意工具服务器。MCP 流量经过一个掌管凭据与白名单的网关，正如模型网关掌管 token 流量（第 41 章）。
  • 一种遥测格式，OTel。 每个组件都发出 gen_ai.* span，可观测性后端可随时替换，评测循环也能读取任何轨迹（第 43 章）。

三条弧线

本书沿三条弧线搭建了这套技术栈。参考架构正是它们交汇之处。逐条走一遍，是看清整个系统如何流动的最快方式。

从聊天机器人到智能体

聊天机器人是一次模型调用：提示词进，补全出。智能体则是绕着这次调用的一个循环：模型发出一个工具请求，运行时执行它，把结果喂回去，模型再决定下一步做什么，可能反复许多轮（第 21 章、第 23 章）。三样东西把前者变成后者，三样都出现在 图 44.1 的右侧与顶部。

  • 经检索的接地。 智能体不去轻信模型的权重，而是检索当下的、私有的或权威的上下文并注入（第 25 章、第 42 章）。2026 年的共识流水线是混合搜索（BM25 加密集向量，以倒数排名融合 RRF 合并）后接一个重排器，其中嵌入与重排模型经由网关调用，于是它们像任何其他模型调用一样被计费与限额。优先用检索，而非把百万 token 的上下文窗口塞满：长上下文很贵，200K token 以上的价格断崖（第 37 章）往往让检索既更便宜也更忠实。
  • 经 MCP 与沙箱的工具。 读取结果是容易的那一半。行动，运行代码、打 API、写文件，才是安全不再关乎模型、转而关乎运行时的地方（第 41 章）。网关上的越狱过滤器对模型被诱导发出的 rm -rf 毫无办法。执行层是沙箱：一个 microVM（Firecracker，E2B、Fly、Vercel 在用）或用户态内核（gVisor，Modal 在用），它框住爆炸半径，配以默认拒绝出网、硬超时，以及对不可逆动作的人在回路关卡（第 34 章）。
  • 经检查点的记忆。 长跑的智能体必须能从重启中幸存，所以它的状态存在一个持久化的、带检查点的存储里（LangGraph 的 checkpointer、Pydantic AI 的持久化执行），而非进程内存里（第 22 章）。这让人能在任务中途暂停、检视并续跑。

约束箭头沿这条弧线向下贯穿：智能体不可能比它之下的网关、服务与沙箱层更可靠。这恰恰是为何「持久化执行」与「检查点」成了 2026 年框架的头条功能。它们是框架试图从下层故障中幸存的努力。

从推理到训练

一套 2026 技术栈的大部分是推理：在 OpenAI 接缝后服务一个固定的模型。网关这一个地址能挡在托管 Claude 端点前，也能挡在自己服务的模型前，还能挡在自己训练的模型前（第 39 章、第 40 章）。从推理到训练这条弧线，就是从租用能力到拥有能力的弧线，网关正是让两者无缝互换的东西。

经济性决定你落在弧线的何处。用闭源 API，不运行推理服务器：实验室掌管批处理、KV 缓存、投机解码与加速器（第 16 章），你只需要按需调整（缓存输入定价、优先级档位）。当量与掌控力足以撑起时，跨到自托管服务（默认 vLLM，前缀密集的智能体与 RAG 流量用 SGLang），每 token 成本就从一张厂商账单变成自己调度的 GPU 账单。沿弧线再往前，微调（第 9 章）或后训练一个模型，把结果服务在同一道接缝后。训练运行本身落在算力地板上，由 Slurm 或带 gang 调度插件的 Kubernetes 进行 gang 调度（第 31 章、第 30 章）。

决胜变量是持续利用率。在大约半块 GPU 的稳定负载之下，无服务器或托管推理平台（Modal、Baseten、Fireworks、Together）比为闲置预留硬件付费更便宜。在它之上，neocloud 或超大规模云上的预留集群胜出。这里的约束箭头来自 第 3 章：一个 token 的服务成本是永远在付的，这也是为何把更小的模型过度训练一次，比不训练而多次租大模型更划算。因此模型的尺寸由它一生将解码多少 token 决定，而不只由训练预算决定。

改一改下面两个价格旋钮，看看自建与租用的交叉点落在哪里：在它之下无服务器胜出，在它之上固定的预留账单胜出。

import numpy as np
# Illustrative figures only (mid-2026 indicative, not real quotes). Tune freely.
serverless_per_gpu_hour = 4.0   # $/GPU-hour, pay only while running
reserved_per_gpu_hour   = 2.0   # $/GPU-hour, billed 24/7 whether idle or not
u = np.linspace(0.01, 1.0, 100)                      # sustained utilization
serverless = serverless_per_gpu_hour * u * 24 * 30   # pay per busy hour
reserved   = reserved_per_gpu_hour * 24 * 30          # flat monthly bill
crossover = reserved_per_gpu_hour / serverless_per_gpu_hour
print(f"crossover utilization = {crossover:.0%} of one GPU")
print("below it serverless wins, above it reserved wins")
import matplotlib.pyplot as plt
plt.plot(u, serverless, label="serverless / managed (pay per use)")
plt.axhline(reserved, color="C1", label="reserved (flat 24/7)")
plt.axvline(crossover, color="gray", ls="--")
plt.xlabel("sustained utilization (fraction of one GPU)")
plt.ylabel("monthly cost ($)")
plt.legend(); plt.title("Build vs rent crossover"); plt.show()

从用量到评测

第三条弧线合上整个循环。应用发出的每一次模型与工具调用都是用量，每一单位用量都是能观测、能打分的东西（第 43 章）。一个在公开榜单上拔得头筹的模型在产品里仍可能表现糟糕，因为基准衡量的是通用能力（第 27 章），而应用跑的是一条特定提示词，叠加检索上下文，运行在一个智能体循环里。

这个循环有两半，在 OTel 接缝处交汇。可观测性捕获轨迹：一个请求的完整树形，每一次 LLM 调用、检索与工具调用，每个 span 上都有输入、输出、计时、token 与成本。评测用确定性断言、基于参考的指标，以及 LLM 作为裁判（第 28 章，由第二个模型按一套校准过的评分细则给第一个打分）来为这些轨迹打分。两者相连是因为评测的正是所观测的轨迹：一条在线裁判未通过的生产轨迹，会被提升进离线回归套件，由它为下一次发布把关（第 29 章）。因为应用、评测与裁判统统调用网关，两个模型间的 A/B 就是一条路由规则，裁判跑在一把受限、预算封顶的虚拟密钥上。

这条弧线反哺另外两条。评测数据集变成训练弧线的偏好数据，失败的智能体轨迹变成加固智能体弧线的固定用例。三条弧线不是并行轨道，而是同一个循环。

选一套参考栈

没有唯一正确的技术栈，但有三种覆盖大多数团队的原型。行是各层，挑出与约束相符的那一列，然后顺着它往下读。这些是供改编的起点，日期为 2026 年年中，并非排名。

网关 OpenRouter 或 Cloudflare AI Gateway（托管） 自托管 LiteLLM，虚拟密钥 + 预算 Envoy AI Gateway 或 agentgateway（集群内）

算力 无服务器 GPU（Modal / Baseten / Fireworks） 预留 neocloud（CoreWeave / Lambda），Slurm + K8s 带 Volcano/KAI gang 调度的 K8s，Kueue 配额

表格之下那条耐久的建议是：尽量减少新的活动部件，把质量预算花在见效的地方（检索与重排优于更花哨的向量库，校准过的裁判优于更多基准），让每一层都经由那三份协议可寻址，于是每一层都可替换，永远不要把单一厂商硬编码进去。起步的原型不是终点的原型，正是那些协议让迁移保持便宜。

接线：接缝处的代码

要紧的胶水不是工具教程，而是接缝处的代码，那寥寥几行让各层得以互换。两段代码展示承重的模式：一段把托管与自托管模型统一起来、带回退的网关配置，以及一个用虚拟密钥指向那个地址的智能体。

先看网关。这段 LiteLLM 代理配置暴露一个别名 smart，它在托管模型与自托管模型之间做负载均衡或回退。应用永远不知道是哪个模型服务了这次请求（草图；确切 schema 见 LiteLLM 文档）。

# litellm proxy config: one alias, hosted primary with a self-hosted fallback
model_list:
  - model_name: smart                          # the name the app requests
    litellm_params:
      model: anthropic/claude-opus-4-8
      api_key: os.environ/ANTHROPIC_API_KEY    # provider secret stays server-side
  - model_name: smart                          # same alias, fallback target
    litellm_params:
      model: openai/gpt-5.5
      api_key: os.environ/OPENAI_API_KEY
  - model_name: local                          # self-hosted, behind the same seam
    litellm_params:
      model: hosted_vllm/your-open-weight-model
      api_base: http://vllm-svc:8000/v1

litellm_settings:
  fallbacks: [{ "smart": ["local"] }]          # if hosted "smart" fails, use local
  num_retries: 2
# virtual keys, team budgets, and spend caps are minted via the /key/generate
# API and the proxy UI, not this file.

再看智能体。它持有的是一把网关虚拟密钥，而非提供商密钥。它检索上下文、运行一个工具，且永远不知道是哪个模型作答。这里的 MCP 工具为简洁起见放在进程内；生产中它在 MCP 网关后经 HTTP 暴露，智能体代码几乎不变，这正是 MCP 作为线协议而非库 API 的意义所在（Claude Agent SDK 形态；具体 API 见 SDK 文档）。

from claude_agent_sdk import tool, create_sdk_mcp_server, query, ClaudeAgentOptions

@tool("search_docs", "Retrieve grounding context for a query", {"q": str})
async def search_docs(args):
    # hybrid retrieve + rerank; embed/rerank calls go through the gateway too
    hits = await retriever.hybrid_search(args["q"], top_k=8)
    return {"content": [{"type": "text", "text": "\n\n".join(h.text for h in hits)}]}

server = create_sdk_mcp_server(name="rag", version="1.0.0", tools=[search_docs])

async for msg in query(
    prompt="Using the docs, summarize our refund policy and cite the source.",
    options=ClaudeAgentOptions(
        mcp_servers={"rag": server},
        allowed_tools=["search_docs"],
        # model access resolves through the gateway base_url + a scoped virtual
        # key, never a raw provider credential. Swapping the model behind "smart"
        # or capping this agent's spend is a server-side change with no redeploy.
    ),
):
    print(msg)

评测套件以同样的纪律合上循环。一段 Promptfoo 配置把其 provider 的 apiBaseUrl 指向网关，并用一个不同的模型家族作裁判，跑在它自己的预算封顶虚拟密钥上（第 43 章）。系统里的每一道接缝，模型调用、工具调用、检索与裁判都在同样的两个地址（模型网关与 MCP 网关）交汇，并发出同样的 span 格式。正是这一点让这套架构成为一个系统，而不是各自为政的一堆工具。

能力、效率、信任之镜

能力：靠这三份协议，系统比任何单层都更强。一个接地的、会用工具的、持久的智能体，每一步由最适合的模型支撑。每一层各司其职、同类最佳，而它们还能组合。效率：网关把按任务路由、回退与成本封顶变成配置问题，需要时升级到昂贵模型，负载大时回退到廉价模型，无需改代码。信任：虚拟密钥托管让密钥不出客户端与沙箱，OTel 基座让轨迹跨厂商携带，评测循环把「感觉更好」变成可为发布把关的数字。这三者同时成立，才值得这样去接线。到 2026 年年中，那些协议已成熟到足以让三者成立。本书开篇所讲的生命周期，从算力到受治理的行为，终于能端到端地贯通同一套架构。
