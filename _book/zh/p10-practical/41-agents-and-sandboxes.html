智能体、框架与沙箱

这一章是实践层面的。它要把 第 21 章 的智能体架构、第 23 章 的运行框架、以及 第 34 章 的授权模型，转换成工程师在 2026 年真正要做的选型和接线决定。目标不是列举所有框架，而是给你一套清晰的选择标准，以及一个稳妥的默认方案。

智能体运行时由三部分组成。2026 年很多混乱就源于把这三块混在一起了：

  1. 框架 / SDK 是那个循环。模型本身只输出 token。要让它调工具、读结果、决定下一步、记住之前的轮次、把工作递给另一个智能体、停下来等人类、在崩溃后恢复，你需要一个控制循环和它周围的基础设施。
  2. MCP（Model Context Protocol） 是工具通信的标准协议。它之于工具集成的地位，就像 OpenAI Chat Completions 之于模型调用。一个工具服务器写一遍，就能被所有框架复用。
  3. 沙箱 是执行的基础。模型一旦能执行代码，安全问题就从模型这一侧转到运行时。沙箱是那个隔离的计算环境，代码在其中跑。

一条贯穿全章的主线：框架、工具和沙箱都把密钥和模型访问保留在外面，只通过有管控的通道伸进来。模型走网关虚拟密钥，凭据走短时效的受限令牌，网络走默认拒绝加白名单。把这套原则做对了，具体的产品就变成了可以互换的选择。

截至 2026 年年中下文的一切都是一份带日期的快照（2026 年 6 月）。在这个品类里，版本号、价格与「最适合」的判断

变动很快。把排名和具体数字当作有来源、可核验的，而非永恒的事实，在投入之前请到各项目自身的文档核对当前值。耐用的内容是类别与权衡，而非版本字符串。

框架：全景

功能对比表会掩盖真正的决策点。真正要紧的是框架怎样组织智能体循环，这决定了你能表达什么、要写多少样板代码、控制权落在谁手里。五种主要模式覆盖了整个领域，直接对应 第 21 章 讲的那些循环结构：

  1. 图 / 状态机（LangGraph、Google ADK、Pydantic AI 的 pydantic-graph）。你声明节点和边；运行时遍历这个图，持久化一个有类型的 State，支持循环、并行分支、条件分支、从检查点恢复。表达能力最强，控制最细，代码量最多。唯一能原生处理「智能体 A 然后 B 再回 A」和「B 与 C 同时跑」的。
  2. 线性交接链（OpenAI Agents SDK）。一组小原语；智能体通过交接对话来委派，接收方看到完整会话。环形或并行的逻辑需要手写。到第一个可用的智能体最快。
  3. 运行框架 / CLI 引擎（Claude Agent SDK）。循环就是 第 23 章 里的 Claude Code 引擎：内置实际文件系统、bash、网页搜索、自动上下文压缩，你用 hook、进程内 MCP 工具和 subagent 来扩展。做「模型在代码仓库里工作」这类事，没有别的框架能比。
  4. 角色 / 团队编排（CrewAI）。你定义专门角色和目标；多个角色协作。当问题自然分解成不同的角色时很顺手，粒度不如图那么细。
  5. 模型优先的自主循环（AWS Strands）。系统提示加工具，由模型驱动。脚手架最少，确定性最少。

工具和记忆的处理是第二个维度，MCP 已经把这块大部分统一了。工具要么是原生函数工具（被装饰过的函数，其签名成为 schema），要么是 MCP 服务器（通过 stdio/HTTP 外接，或进程内）。记忆从「框架每轮重放消息列表」（OpenAI Sessions，最简单）到「带检查点的可恢复 State」（LangGraph、Pydantic AI 的持久化执行）不等。关键问题是你是否必须在任务中途能熬过重启。如果是，需要检查点机制，不是消息列表。

如何具体地选

  • 选 LangGraph 的情况：工作流确实是个图，需要循环、并行分支、审批门、长时运行、要求从崩溃恢复。为了这些控制，接受多一些代码量。
  • 选 OpenAI Agents SDK 的情况：想用最短的路径搭出中等复杂度的生产智能体，重视一组小而易懂的原语。
  • 选 Claude Agent SDK 的情况：智能体的工作就是 Claude 在文件系统或命令行上做事。这类编码智能体的开发体验无人能敌。
  • 选 CrewAI 的情况：问题能清晰地分成不同的专门角色，想快速建个多智能体原型。
  • 选 Pydantic AI 的情况：在 Python 里想要类型安全、经验证的结构化输出和持久化执行。
  • 选 LlamaIndex 的情况：最难的部分在检索和文档解析，不在编排。用它做数据层，编排保持轻。
  • 选 Mastra 的情况：团队主要用 TypeScript。
  • 选 Google ADK 或 AWS Strands 的情况：已经锁定在那个云平台上，想要官方工具。
  • 选 Microsoft Agent Framework 的情况：是 .NET/Azure 企业。这是 AutoGen 和 Semantic Kernel 的官方继任者，那两个已经只维护了。

一个稳妥的默认。 第一次构建正式智能体的团队，按循环原型选，别按品牌偏好。如果是编码、运维或文件系统智能体，从 Claude Agent SDK 开始：直接给你一个可用的循环，配真实工具、上下文压缩和 MCP，通过 hook 和 subagent 扩展。如果是中等复杂度的通用任务/工具智能体，从 OpenAI Agents SDK 开始：半天就能学会那套原语，与供应商无关，有内置追踪。当工作流超出线性链条、需要循环、并行分支、审批门或持久恢复能力时，升级到 LangGraph。那次升级是成长的信号，不是失败。

约束箭头框架不可能比它下面的网关和服务层更可靠（@sec-serving-stack，@sec-wiring-stack）。「持久化执行」和「检查点」之所以成为 2026 年的主要特性，就是框架在想办法活过下层的故障。让框架指向一个有虚拟密钥的模型网关，而不是原始的供应商凭据，这样下层的治理（允许列表、预算上限、模型切换）就变成服务端的一个改动，不用重新部署智能体。

MCP：万物之下的工具层

MCP 是这个故事的另一半。它是那个协议，让一个工具服务器写一遍就能被所有框架使用。「框架 X 支持哪些工具」这个问题就消失了，答案是「任何 MCP 服务器」。到 2026 年，MCP 已经是表里几乎所有框架下面的标准工具层。

规范状态，截至 2026 年年中：

  • 稳定版：2025-11-25。 有状态，有 initialize/initialized 握手和每会话的状态。传输是 stdio（本地子进程）或 Streamable HTTP（远程服务）。

  • 候选版 2026-07-28（2026 年 5 月 21 日发布），维护者说这是发布以来最大的改动。核心是无状态内核：删除 init 握手和会话状态，把协议元数据放在 _meta 里，加上路由头（Mcp-Method、Mcp-Name），让负载均衡器可以不读消息体就路由。目的是在普通 HTTP 基础设施上做横向扩展，任何服务器实例都能处理任何请求。它还正式化了独立版本的扩展（MCP Apps 用于服务端渲染 UI、Tasks 用于异步工作），加上 12 个月的弃用期和合规测试套件。相比 2025-11-25 这是破坏性变更。依赖无状态行为之前，确认最终发布日期和你的客户端/服务器支持情况。

  • 注册表和发现。 有一个带命名空间验证的官方 MCP Registry。MCP Server Cards（一种 .well-known 元数据格式）让注册表和爬虫无需实时连接就能发现服务器。常引用的「500+ 个公开服务器」是一个变动的、二手的数字。

生产里不会让每个智能体直接连接到任意 MCP 服务器。要让 MCP 流量经过一个受管理的代理（「MCP 网关」，agentgateway 之类），它做认证、允许列表、审计，就像模型网关管理 token 流量那样。无论哪种情况，框架都是说 MCP；一个工具是本地子进程、远程 HTTP 服务还是进程内函数，智能体代码几乎不用改。这种可移植性正是 MCP 作为线缆协议而不是库 API 的意义。

进程内 MCP 工具的一个最小例子，用 Claude Agent SDK 的形式。具体的当前 API 见 SDK 文档。

from claude_agent_sdk import tool, create_sdk_mcp_server, query, ClaudeAgentOptions

@tool("lookup_order", "Look up an order by id", {"order_id": str})
async def lookup_order(args):
    row = await db.fetch_order(args["order_id"])
    return {"content": [{"type": "text", "text": row.summary()}]}

server = create_sdk_mcp_server(name="ops-tools", version="1.0.0", tools=[lookup_order])

async for msg in query(
    prompt="Refund the late order for customer 4471 and explain why.",
    options=ClaudeAgentOptions(
        mcp_servers={"ops": server},
        allowed_tools=["lookup_order", "Read"],
        # model access resolves through the gateway base_url + virtual key,
        # not a raw provider credential
    ),
):
    print(msg)

同一个智能体也可以改成指向 MCP 网关后面、经 HTTP 接入的外部 MCP 服务器。框架代码几乎不用改。

沙箱：执行的基础

沙箱是一台一次性的、隔离的计算机，交给智能体在里面运行不信任的代码。模型写一段 Python、一条 shell 命令、一次 git 操作，或一整套开发流程，这些代码跑在某个地方，不是你的笔记本、不是你的生产集群、也不与其他租户的密钥共享内核。

安全论证很直白，值得铭记：智能体一旦能执行代码，网关上的越狱过滤器对 rm -rf、挖矿程序或被诱导的数据泄露 curl 完全无效。2026 年的安全共识（Firecrawl 和其他）是：唯一有效的防御是隔离代码运行的物理环境，不是在系统提示里恳求。这是 第 34 章 的实战面：运行时而不是提示才是执行边界。

两种隔离模型占主导，二者之间的选择基本就决定了一切：

  • 微虚拟机隔离（Firecracker、Cloud Hypervisor、Kata）。每个沙箱是一台真实的、最小化的虚拟机，有自己的来宾内核，通过硬件虚拟化（KVM）与主机分隔。这是对不信任代码最强的常见部署边界，和 AWS Lambda 一脉相承。Firecracker 报告可以在约 125 毫秒内启动用户代码，每主机每秒可创建约 150 个微虚拟机（项目文档，2026 年数据）。

  • 用户态内核 / gVisor 隔离。 一个用户态内核截获系统调用，来宾永远不直接和主机内核通话。生产级别的（Google Cloud Run 就用这个），用微虚拟机硬件边界的一丝换取自定义镜像更快的启动。Modal 用这个模型。

第三个更弱的等级是普通容器，共享主机内核，很常见，但对于不信任的代码应该视为软边界，除非用 gVisor 或微虚拟机来加强。第四个是 V8 isolate（Cloudflare Dynamic Workers），更快，但只能运行沙箱化的 JS/WASM，不能运行任意操作系统。

Runloop 双层（VM + 容器） 托管；免费 + 用量、Pro 档、企业版 你构建编码智能体，想要挂起/恢复的 devbox 加内置 SWE 式基准 差异点是评测/基准 + 挂起/恢复工具，而不只是隔离
Northflank 微虚拟机（按基础设施 Kata/gVisor） 自助 + 企业；更低的标称 vCPU/GB 费率 你想要一个平台同时做应用部署与智能体代码执行，且计算费率更低 隔离随底层基础设施而变；定位于成本 + 自带云
Browserbase（+ Anthropic Managed Agents） 被隔离的 headless Chromium 托管；按会话 / 按浏览器分钟计费 智能体的工作在浏览器里（网页自动化、computer-use），而非 shell 驱动 Anthropic 的 Managed Agents（beta，2026）：Anthropic 跑循环，Browserbase 提供被隔离的浏览器
Firecracker（项目） 微虚拟机 VMM 本身 开源（Apache 2.0），源自 AWS 沙箱化是你的核心业务，你想运营自己的微虚拟机机队 不是你直接使用的产品；它是 E2B、Fly、Vercel、Lambda 之下的隔离原语
Cella（latere.ai） 作者自有运行时 Latere 产品族；公开文档有限 Latere 栈，以及作为本书的一个范例 披露为作者自有的基础设施；用于示例，而非中立推荐。 一次 API 调用启动一个具名的临时或持久沙箱
争议所在微虚拟机和 gVisor 之间是真实的权衡，不是已解决的问题。微虚拟机（Firecracker）给出最强的硬件边界，但历史上在冷启动和镜像构建灵活性上成本更高。gVisor 用略薄的边界换自定义镜像更快的启动。普通容器用真实的隔离风险换速度和密度。随着 gVisor 和微虚拟机的成本与延迟曲线在 2026 年移动，某个威胁模型的「正确」选择也会跟着变。唯一持久的说法是：对真正对抗性的、模型生成的代码，共享内核的容器是软边界，硬件或用户态内核隔离才是可证明的那条线。

如何具体地选

决策由三个维度主导：隔离强度对启动延迟、临时对持久、以及智能体需要做什么（shell、GPU，还是浏览器）。

  • Pick E2B 的情况：想要一个流行的、为智能体设计的、用微虚拟机隔离的代码沙箱，有真正的开源 SDK 和可选自托管出路，运行短期 Python/JS 工具调用。
  • Pick Modal 的情况：智能体需要在同一个隔离环境里运行不信任代码并且触及 GPU。
  • Pick Fly Machines / Sprites 的情况：想要微虚拟机的控制权，为可复现的评测运行做快照/恢复，且空闲时零成本。
  • Pick Vercel 或 Cloudflare Sandbox 的情况：应用已经在那个平台上。比较 Cloudflare 的边缘分布和 V8 快速路径，对比 Vercel 的 Firecracker 沙箱和预置内存计费。
  • Pick Runloop 的情况：构建编码智能体，想要挂起/恢复的 devbox 加内置 SWE 风格的基准。
  • Pick Browserbase（或 Anthropic Managed Agents） 的情况：智能体在浏览器里操作，而不是 shell。
  • Self-host on Firecracker 的情况：只有当沙箱化是你的核心业务。

价格对比很复杂。「仅活跃 CPU」的提供商仍可能对预置内存按整个生命周期计费（Vercel），平台最低费用或 Durable-Object 费用（Cloudflare）藏在标称 vCPU 费率下面。永远要按自己的实际使用情况建模（生命周期、空闲比例、并发），而不是按小时标价。

改变空闲比例看看，纯活跃 CPU 的账单和按整个生命周期对预置内存计费的账单之间差距如何拉开。

# A bursty agent: short CPU spikes between long idle waits on the model.
lifetime_s = 600          # 10-min box, alive the whole task
cpu_price = 0.000040      # $ per active vCPU-second
mem_price = 0.0000060     # $ per provisioned GB-second (billed even while idle)
mem_gb = 2.0
for idle in [0.0, 0.5, 0.8, 0.95]:
    active_s = lifetime_s * (1 - idle)
    cpu_cost = active_s * cpu_price
    mem_cost = lifetime_s * mem_gb * mem_price   # full lifetime, not active only
    total = cpu_cost + mem_cost
    mem_share = 100 * mem_cost / total
    print(f"idle={idle:>4.0%}  active-CPU=${cpu_cost:.4f}  "
          f"provisioned-mem=${mem_cost:.4f}  total=${total:.4f}  "
          f"mem={mem_share:.0f}% of bill")

要点：空闲比例越高（智能体越多地等待模型），预置内存费用就越主导总账单，即使在一个「仅活跃 CPU」的提供商上也是如此。

一个稳妥的默认。 2026 年要构建会运行代码的智能体的团队，默认用 E2B 做托管的、微虚拟机隔离的执行：为智能体设计、有真正的开源 SDK、有自托管出路、隔离强（Firecracker）、按秒计费适合突发工具调用。智能体需要盒内 GPU 时，默认改成 Modal。特别想要为可复现评测做快照恢复（第 43 章）且空闲零计费时，默认 Fly Machines / Sprites。对于 Latere 栈，对应的内部方案是 Cella，已披露为作者自有基础设施，所以不是中立之选。

安全地接线在一起

智能体框架是消费者，不是中心。它通过网关调用模型，从检索拉取接地信息，通过 MCP 触及工具，在沙箱里运行代码，发出评测和可观测层读的追踪。图 41.1 是生产里站得住的形状。

三件事让它站得住：

  1. 框架从不持有供应商密钥或原始凭据。 它持有一个限定到模型允许列表和预算的网关虚拟密钥，MCP 流量通过一个拥有工具凭据和允许列表的网关。把一个模型换成另一个，或给失控的循环设限，是一次服务端改动。

  2. 状态住在检查点里，而不是进程内存里。 一个持久的 State（LangGraph 的检查点、Pydantic AI 的持久化执行）才能让长时智能体活过重启，也让人类能暂停、检查、恢复。

  3. 沙箱把密钥、模型访问和网络留在盒子外面。 它们只通过狭窄、可审计的通道进来：凭据用短时效的受限令牌，模型用网关虚拟密钥，网络用默认拒绝加白名单。

一个最小的安全用法配置示例。结构比具体的键名更重要，按你的沙箱提供商调整。

sandbox:
  isolation: microvm          # firecracker/gvisor; not a bare container for untrusted code
  lifetime: ephemeral         # destroy after the run: nothing persists, nothing leaks
  timeouts:
    per_tool_call: 30s
    per_task: 10m
    max_lifetime: 30m
  network:
    egress: deny              # default-deny
    allow: ["pypi.org", "api.internal.example.com"]
  secrets:
    inject: none              # no raw provider keys in the box
    model_access_via: gateway # short-lived scoped virtual key only
  audit:
    log: [commands, network_requests, file_writes]   # immutable trail
  approval:
    require_human_for: [payments, production_writes]

这些是 2026 年来源里反复出现、用能力、效率、信任之镜总结本章的安全实践：最小权限、短时效凭据；把每个工具或浏览器的输出当作不信任的输入，把「思考」和「行动」分开；默认拒绝加显式白名单的出网；工具、任务、沙箱生命周期各级的硬超时；不可变审计日志；默认临时使状态和凭据不堆积；对不可逆操作的人在环关卡。框架选择是可逆的。网关、沙箱和审批的原则才是让它保持可逆的。
