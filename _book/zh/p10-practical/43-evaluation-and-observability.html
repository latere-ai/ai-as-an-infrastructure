评测与可观测性

榜单上的第一名模型，在你的产品里仍然可能翻车。基准测试衡量的是某个固定数据集上的通用能力；你的应用却跑的是特定的提示词，加上你自己的检索上下文，在智能体循环里处理源源不断变化的真实用户输入。弥合这条裂缝需要两套东西，到 2026 年年中，它们已经基本合并成一类工具了。本章就是实用指南：怎么选，怎么接。

第 27 章 抽象地衡量模型的能力，第 28 章 讲开放式输出的评分方法，第 29 章 讲多步智能体的评测。本章衡量的是你正在运行的系统。它依赖服务层（第 39 章）和模型网关（第 44 章），产出反馈信号回到智能体（第 41 章）和微调（第 40 章）：评测数据集会变成偏好数据，故障的真相在智能体轨迹里浮出来。

截至 2026 年年中这是一份有时间戳的快照（2026 年 6 月）。这个领域跑得快，价格、版本、收购、「最适合用什么」的判断都在变，2026 年更是大整合频繁。下面的具体金额和排名都有来源，但只是个参考值，不是永远的事实。长期投入前记得重新查证当前的数字和产品路线图。重点是抓住更经久不衰的东西：品类、权衡、怎么接线。

循环的两半

**评测（Evaluation）**问的是「输出好不好」，按你的标准来打。可以离线做（筛选过的数据集、CI 里、发版前），也可以在线做（生产流量采样、持续计分）。基本单位是分数，有三种混着用：

  • 确定性断言：正则、JSON-schema 校验、精确匹配、延迟预算、成本预算。便宜、快，是第一道防线。
  • 基于参考的指标：BLEU、ROUGE 这类，以及它们在检索里的表亲，如上下文精确率、召回率、忠实度。
  • LLM 作为裁判：第二个模型按评分细则给第一个打分。大规模评估开放式输出质量，这是唯一实用的办法，第 28 章 的重点就在怎么做而不自欺。

**可观测性（Observability）**问的是「到底怎么回事」。它捕获一条轨迹（trace）：请求在系统里流动时的完整树，每一次 LLM 调用、检索、工具调用、嵌套的智能体步骤，每个 span 都记下输入、输出、耗时、token 数、成本。没有它，你就只能靠读平铺的日志来调试一个非确定性的分布式系统。

两部分相连：你评的就是观测到的轨迹。生产轨迹就变成了测试用例。裁判在采样的 span 上跑，产出在线分数。仪表盘发现的一次回归，就变成离线套件的新测试。观测、打分、筛选、重测这个循环，就是「持续评测 LLM 应用」的核心做法，也就是本章后面那张图要说的事（图 43.1）。

2026 年的洗牌

2026 年初的两起收购重塑了这个领域，也说明了方向：独立的评测工具和可观测性工具，正在融进更大的数据或模型平台。

  • OpenAI 收购了 Promptfoo（2026 年 3 月 9 日宣布），同时停用自家的 Evals 托管产品（10 月 31 日转只读，11 月 30 日关停），用户转向 Promptfoo 和 Datasets。开源仓库 openai/evals 还在，托管仪表盘没了。
  • ClickHouse 收购了 Langfuse（2026 年 1 月 16 日，和 ClickHouse 4 亿美元 D 轮融资一起宣布）。Langfuse 表示开源和自托管的承诺依然有效。

重点不是哪家公司拿了哪个工具，而是这里的变化是真的，所以要选那些数据和埋点能让你带走的工具。OpenTelemetry 就是这样一个选择。

如何选择

先分清两类：能力评测和应用评测，用的工具和做的事都不一样。

约束箭头服务层定下了你评测套件的形状。因为评测和裁判指向模型网关（@sec-wiring-stack）而不是直连提供商，两个模型的 A/B 对比就变成了一条路由规则，不用改代码；裁判的凭据也变成了有预算上限的虚拟密钥，不是裸露的提供商密钥。@sec-serving-stack 选的那个网关，就是让在线评测成本保持低廉的关键。

衡量模型的能力时，选能力套件：对比训练检查点、验证微调（第 40 章），或复现榜单数字。任务涉及智能体、工具使用、安全问题就用 Inspect，经典学术基准用 lm-evaluation-harness。

衡量你的系统时，选应用评测工具：这个提示词、这条 RAG 流水线、这个智能体，对着你产品真正关心的标准。应用评测里，四个维度决定怎么选：

轴 选这个 何时
CI 原生 vs 平台原生 Promptfoo（配置/CLI）或 DeepEval（pytest） 评测必须住在仓库里、零外部账号就能为合并把关
Braintrust 或 LangSmith 你想要托管 UI 让非工程师可视化地筛选数据集、对比运行
自托管 vs 托管 Langfuse 或 Phoenix 数据驻留、成本管控或厂商中立要紧，且你能运维基础设施
LangSmith、Braintrust、Confident AI 你宁愿不自己运维，愿为打磨付费
OTel 原生 vs 专有 SDK Phoenix / OpenInference 你想要一套能瞄准多后端、避免锁定的埋点
LangSmith、Braintrust 开箱更顺滑，代价是把代码耦合到单一厂商
红队是否在范围内？ Promptfoo 你需要最深的内置对抗扫描（OWASP LLM Top 10、越狱、PII、提示注入）

LLM 作为裁判：成本对信任

裁判比人工评审便宜个 500 到 5000 倍，能接近人与人的一致程度，但前提是得校准过。没校准的裁判就是个有信心的骗子。到 2026 年年中，第 28 章 深入讲的共识做法是这样：

  • **对人工标注的样本验证。**报告 Cohen's kappa 或 Krippendorff's alpha，先把一致度压到 0.80.80.8 左右，再信任裁判把关。
  • **控制位置偏差。**A/B 和 B/A 两个顺序都打分，只统计一致的胜负。
  • **控制啰嗦偏差和自偏好。**千万别用同一个模型家族既生成又评判。
  • 用明确的、按标准拆开的评分细则（G-Eval 风格）。把硬规则拆成检查的 DAG，别用含混的提示词。

改变人工标注的基率，原始一致度还是高，Cohen's kappa 就完了，所以「裁判 90% 同意」说明不了什么。

import numpy as np

# A lazy judge that says "good" almost always, scored against human labels.
# Raw agreement looks great, but Cohen's kappa corrects for chance and collapses.
def kappa(m):
    m = np.array(m, float); n = m.sum()
    po = np.trace(m) / n                       # raw agreement
    pe = (m.sum(0) * m.sum(1)).sum() / n**2    # agreement expected by chance
    return po, (po - pe) / (1 - pe)

n = 1000
for good_rate in [0.70, 0.80, 0.90, 0.95]:
    good = int(n * good_rate); bad = n - good
    caught = int(bad * 0.20)                    # judge flags only 20% of bad answers
    miss = int(good * 0.02)                     # and wrongly flags 2% of good ones
    cm = [[caught, miss], [bad - caught, good - miss]]
    po, k = kappa(cm)
    verdict = "trust" if k >= 0.8 else "do NOT trust"
    print(f"human good={good_rate:.0%}  agreement={po:.2f}  kappa={k:.2f}  -> {verdict}")

一个合理的默认选择

对一个典型团队，交付一两个 LLM 功能、想要持续评测循环但不想单独建平台团队，下面这套栈是开源优先、可自托管、OTel 原生、CI 把关、将来升级到托管平台有条清晰的路。

任务 默认之选 托管替代
可观测性 / 追踪 Langfuse（自托管或免费/Core 云） LangSmith（Plus）或 Braintrust
CI 中的应用评测 Promptfoo（断言、对比、红队）+ DeepEval（pytest 指标） Braintrust / LangSmith 评测模块
模型 / 能力评测 Inspect（智能体、安全）或 lm-evaluation-harness（学术） 托管榜单
埋点 OpenTelemetry GenAI 经 OpenInference 自动埋点 专有 SDK

这个默认值得说两件事。一是变化：Promptfoo 现在是 OpenAI 的，Langfuse 现在是 ClickHouse 的，长期用之前重新看清路线图和许可。二是别加你不需要的平台。已经在 Databricks 的团队用 MLflow 3 Evaluate，在 Weights & Biases 的团队用 Weave，别再自找一个新平台。

接线

循环要经过模型网关（第 44 章）才能闭合。被测应用、评测、裁判都调网关，决不直连提供商。就这一个决定，换模型就变成改配置，裁判凭据始终是有预算上限的虚拟密钥。

下面是一个最小的 Promptfoo 配置，指向网关，在 LLM 裁判前加一层确定性守卫。存为 promptfooconfig.yaml，跑 npx promptfoo@latest eval。

# promptfooconfig.yaml
providers:
  - id: openai:chat:gpt-5            # resolved by the gateway, not OpenAI directly
    config:
      apiBaseUrl: https://gateway.internal/v1
      apiKey: ${GATEWAY_VKEY}        # scoped virtual key, budget-capped
prompts:
  - "Answer using only the context:\n{{context}}\n\nQ: {{question}}"
tests:
  - vars: { question: "...", context: "..." }
    assert:
      - type: is-json                # deterministic guard, runs first and free
      - type: llm-rubric             # LLM-as-judge, calibrated rubric
        value: "Answer is faithful to the context and cites it."
        provider: openai:chat:gpt-5-mini   # judge via gateway, different family

为合并把关，在 CI 里跑这一条，遇到回归就让任务失败：

# CI step: fail the build if any eval assertion regresses
npx promptfoo@latest eval -c promptfooconfig.yaml --no-cache --output results.json
# exit code is non-zero when assertions fail, which fails the pipeline

整个系统的心跳是那个提升步骤。Langfuse 或 Phoenix 里没过在线裁判的生产轨迹，会被拉进上面的 tests: 里，离线套件测的就是你在生产里真正碰到的故障，而不是设计时想象的故障。没这个步骤，你就是两套工具各占一隅；有了它，才能形成循环。

能力、效率、信任三棱镜

能力：可观测性把非确定性系统变成可以调试的东西，评测把「好像更好了」变成能为发版把关的数字。效率：网关让在线裁判的成本降到能连续运行的水平，确定性断言在调裁判前就拦掉便宜的故障。信任：LLM 裁判能信任的程度，取决于它对人工标注的校准；OTel 底层让你能把轨迹和分数从任何改条款的厂商手里带走。三件事都成立，这个循环才值得搭；到 2026 年中，工具终于成熟到能保证这些。
