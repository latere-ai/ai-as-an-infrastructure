训练与微调实践

这是一章实践内容。权重怎么变的理论在 第 9 章（监督微调与参数高效方法）和 第 8 章（优化器分片跨多加速器）讲。这里的问题更直接：现在是 2026 年年中，你有个任务和一笔预算，得选出改权重的工具、接进技术栈剩下的部分，还要判断自己该不该训练。答案既有立场，也有时效。下面讲的大类和权衡会保鲜较久；版本号、价格、排名都是快照，用时再查最新的。

截至 2026 年年中下文的框架、价格、GitHub star 数和营收数字是 2026 年 6 月的快照，各自标注了来源。每词元

价格展示的是定价形态，而非权威报价。凡是标为不确定的，投入预算前要重新核实。大类与选择逻辑变化慢；具体数字以月为单位老化。

这一层及其内容

训练与微调是改权重的那一层，对应只做前向传播的服务层（第 39 章），不同于用上下文驾驭冻结模型的智能体和检索层（第 41 章、第 42 章）。在实际的 2026 年技术栈里，它分成三个子层，容易搞混，但工作方式差别很大。

  1. 分布式引擎。 把模型和优化器状态分片到许多加速器上的底层系统：PyTorch FSDP2 和 TorchTitan、NVIDIA Megatron-Core、Microsoft DeepSpeed（ZeRO），还有 TPU 上的 JAX/XLA（MaxText）。4D 和 5D 并行、FP8 训练、万亿级参数规模都在这儿。第 8 章 会专门讲解机制。
  2. 后训练工具包。 封装这些引擎的高层库，用于监督微调（SFT）、偏好优化（DPO、ORPO）和强化学习（GRPO、GSPO、PPO）：Hugging Face TRL、Axolotl、Unsloth、LLaMA-Factory。大多数团队实际接触的就是这一层。
  3. 参数高效方法与托管服务。 PEFT 库里的 LoRA、QLoRA、DoRA，加上完全隐藏加速器的托管微调 API。

两个 2026 年的主题把这层和全书连起来。FP8 训练已成主流：Google 的 Ironwood TPU 在矩阵单元里原生支持 FP8，Megatron-Core 也提供 FP8 训练，Unsloth 做 FP8 强化学习（Google Cloud, 2026）。更关键的是，RL 后训练已把训练和推理服务融到一块：现代 RL 工具包内嵌推理引擎（通常是 vLLM）来生成 rollout，所以训练的盒子里就装着一个服务的盒子。这正是本章最后讲的接线故事。

第一个岔路：你到底要不要训练？

工具怎么选之前，先回答更难的问题。在 2026 年，对很多任务诚实的默认就是别训练权重。提示工程、少样本示例、检索（第 42 章）和结构化输出已经覆盖了过去经常靠微调才能解决的大部分事。OpenAI 在缩减自助微调的同时，也在推用户用提示缓存、更小的基座模型和 RAG（explainx.ai，二手）。

只有当你需要上下文窗口无法廉价承载的持久行为改变，才去微调：

  • 提示总是偏离的一致输出格式或文风，
  • 基座模型缺少某个狭窄领域的词汇或约定，
  • 把大模型行为蒸馏成小型专用模型带来的推理延迟或成本收益（这就是下面的约束箭头），
  • 靠强化学习对着可验证奖励塑造的能力，即 第 14 章 讲的推理和智能体情形。

都不适用的话，花一周把提示和检索做好，别费力跑训练。

约束箭头服务层向上指，支撑微调最常见的这个理由。一个你已经专化了的小模型，每词元的服务成本远低于 API 背后的大型通用模型（@sec-serving-stack）。当服务量大的时候，这次训练的成本会在推理节省里收回来。这就是 @sec-scaling-laws 里「为推理而过度训练」的逻辑再上一层。所以微调本质上是个穿着*训练*外衣的*服务成本*决策。

改一改下面的数字（一次微调成本和两个服务价格，都是示意），看两条成本线在哪儿交叉：平衡点以下，大型 API 模型便宜；以上，微调小模型赢。

import numpy as np
import matplotlib.pyplot as plt

# Illustrative only: shape of the trade-off, not a quote.
finetune_cost = 50.0      # one-time fine-tune run, USD
big_price = 5.0           # large API model, USD per 1M tokens served
small_price = 0.5         # fine-tuned small model, USD per 1M tokens served

vol = np.linspace(0, 40, 200)            # millions of tokens served
big_total = big_price * vol              # no training, pay per token
small_total = finetune_cost + small_price * vol

break_even = finetune_cost / (big_price - small_price)
print(f"break-even at {break_even:.1f}M tokens served")

plt.plot(vol, big_total, label="big API model")
plt.plot(vol, small_total, label="fine-tuned small model")
plt.axvline(break_even, ls="--", color="gray")
plt.xlabel("tokens served (millions)"); plt.ylabel("total cost (USD)")
plt.legend(); plt.title("When does a fine-tune pay for itself?")
plt.show()

参数高效方法

这些是技术，不是产品；活在 PEFT、Unsloth 和 TRL 里。为什么低秩更新够了，理论见 第 9 章。

  • LoRA。 低秩适配器，默认选。合并进基座权重后推理没额外延迟。
  • QLoRA。 4-bit（NF4）冻结基座加 LoRA；约 1K 到 50K 样本时单 GPU 的甜区。
  • DoRA。 权重分解 LoRA（幅度加方向）；收敛更好，大数据量时值得，约 50K 到 500K 样本。
  • rsLoRA。 高秩用的秩稳定 LoRA。
  • 更新的 arXiv 变体（RandLoRA、激活空间方法）存在，但不是默认。视为前沿、生产未验证（AppScale 2026）。

如何选择

一旦确定真的需要训练权重，四个问题就能定下工具。

运行规模。 一块消费级或单块 GPU 选 Unsloth，因为有专用 kernel 和低显存。几块 GPU 配置即代码选 Axolotl 或 LLaMA-Factory。多节点预训练或继续预训练选 TorchTitan/FSDP2、Megatron-Core，或 TPU 上的 MaxText。

生态。 NVIDIA GPU 且想要厂商支持，选 Megatron-Core/NeMo。PyTorch 原生且能改，选 FSDP2/TorchTitan + TRL。TPU 选 JAX/MaxText。纯 Hugging Face 肌肉记忆就选 TRL。

方法。 文风或格式加小数据选 QLoRA。更深的领域迁移加更多数据选 DoRA 或高秩 LoRA。结构性领域变化加 500K 以上样本选 全量微调。针对奖励的推理或智能体行为选 Unsloth、TRL 或 torchforge 的 GRPO/GSPO（第 14 章）。

自托管还是托管。 托管赢在首次运行时间、无需 GPU 运维、弹性成本和可预测按词元定价。自托管赢在数据驻留、IP 控制、非常规配方、可摊销硬件的重复大型运行，以及避免厂商锁定或突然弃用。注意便利税：Together 按训练词元给 LoRA 计费，还要加单独的按小时专用端点来服务结果，所以便宜的标价不是全部账单。

具体选择：

  • Unsloth 当你在一块 24 到 80GB GPU 上、要最快最省显存的 SFT 或长上下文 GRPO。
  • Axolotl 当你想要几块 GPU 上可复现的 YAML 配置运行，并看重 CI 里的配置即代码。
  • LLaMA-Factory 当你需要模型支持的广度或给非专家用的低代码 UI。
  • TRL 当你在编自定义后训练逻辑、要权威训练器时直接选。
  • TorchTitan/FSDP2 或 Megatron-Core 当你在做真正的多节点预训练或继续预训练。
  • MaxText 当你在 TPU 上。
  • 托管服务 当你没有 GPU 运维意愿、且是标准的 SFT/LoRA/DPO/RFT 工作负载，但要考虑 2026 年的弃用先例，设计好导出路径。

一个合理的默认（2026 年年中）

对一个已确定真的需要微调开放权重模型的典型产品团队，截至 2026 年 6 月：

默认：Axolotl（YAML 配置）建于 TRL + PEFT 之上、做 QLoRA，在租用的 GPU 上（Modal、Runpod 或你自己的云）。可复现，配置即代码契合 CI 与评估（第 43 章），QLoRA 让你停在单块或几块 GPU，权重和数据你自己保。起步配方是 r=16、开启 DoRA、target_modules="all-linear"，难一点的任务再加秩（AppScale 2026）。

  • 备选 A，最大单 GPU 效率或 RL： Unsloth，特别是消费级 GPU 或长上下文 GRPO。
  • 备选 B，完全没有 GPU 运维： 托管服务。Together 用于廉价的开放权重 LoRA/SFT，Fireworks 若想调优和服务一起，Bedrock 若是 AWS 原生。要设计好导出和可移植路径；别以为托管 FT 产品永远存在。OpenAI 在 2026 年 5 月宣布的自助收缩就是个教训。

多节点预训练而非微调的话，改用 TorchTitan/FSDP2 或 Megatron-Core，或 TPU 上的 MaxText。

接进技术栈

2026 年的关键是：RL 后训练如今内嵌了推理层。 GRPO 或 PPO 循环从当前策略生成 rollout，用奖励打分，然后更新权重。生成是瓶颈，工具包就把它交给快速推理引擎，基本都是 vLLM。Unsloth 驱动 vLLM 做 rollout；torchforge 用 vLLM 做生成、TorchTitan 做训练，通过 RDMA 张量存储在两者间搬运权重（PyTorch 博客）。所以你架构图里的训练盒子里装着一个服务盒子。这就是 第 39 章 里那个 vLLM，现在被当训练的一个子组件用。正好说明本书的论点：这些层是一套基础设施。

训练完后，合并适配器或用适配器感知的引擎直接服务，把权重交给网关背后的服务层（第 39 章），并在晋升前跑一遍评估 harness（第 43 章）。检索与智能体层随后消费这个被服务的模型。适配器感知的服务，即一个基座上的众多 LoRA，正是托管适配器平台历来的用途。整个流程汇入 第 44 章 的端到端技术栈。

启动它，然后为服务合并适配器：

# train (single or few GPUs via accelerate)
accelerate launch -m axolotl.cli.train qlora.yml

# merge the LoRA adapter back into the base for adapter-free serving
python -m axolotl.cli.merge_lora qlora.yml --lora_model_dir ./out

合并后的权重交给服务栈。把配置放进版本控制，让一次训练成为一个可审的 diff，和你对技术栈其余部分的要求一致。

收束：能力、效率、信任

透过本书的视角，微调首先是能力杠杆，即提示承载不了的持久行为改变。越来越多是效率杠杆，把大模型蒸馏成廉价可服务的小模型。这也是服务成本约束箭头频繁向上指的原因。还是一个信任面：被微调的模型吸收了你的数据，所以数据驻留、可复现的配置即代码，以及晋升前的评估闸门，不是加分项，而是让你能把权重发出去的控制。2026 年诚实的默认还是先做好提示和检索，只有当行为改变必须活在权重里，才去训练。
