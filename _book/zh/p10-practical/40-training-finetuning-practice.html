训练与微调实践

作者
Changkun Ou
更新于
2026 年 6 月 21 日
阅读时长
约 10 分钟

这是一章实践内容。权重如何变化的理论在 第 9 章（监督微调与参数高效方法）与 第 8 章（把优化器分片到众多加速器上）讲。这里问的更直接：现在是 2026 年年中，你手上有一个任务和一笔预算，要挑选改变模型权重的工具、把它接进剩下的技术栈，还要判断自己到底该不该训练。答案既有立场，也有时效。先立住那些经久耐用的大类和权衡， 至于每一个版本号、价格、排名，都当成一张快照，用时再核实。

截至 2026 年年中

下文的框架、价格、GitHub star 数和营收数字是 2026 年 6 月的快照，各自标注了来源。每词元价格展示的是定价形态，而非权威报价。凡是标为不确定的，投入预算前要重新核实。大类与选择逻辑 变化慢；具体数字以月为单位老化。

这一层及其内容

训练与微调是改变权重的那一层。它对应只做前向传播的服务层（第 44 章），也不同于用上下文引导冻结模型的智能体和检索层（第 46 章、第 47 章）。在实际的 2026 年技术栈里，它分成三个子层，这三层容易搞混，工作方式却很不一样。

  1. 分布式引擎。 把模型和优化器状态分片到许多加速器上的底层系统：PyTorch FSDP2 和 TorchTitan、NVIDIA Megatron-Core、Microsoft DeepSpeed（ZeRO），还有 TPU 上的 JAX/XLA（MaxText）。4D 和 5D 并行、FP8 训练、万亿级参数规模都在这儿。 第 8 章 会讲解机制。
  2. 后训练工具包。 封装这些引擎的高层库，用于监督微调（SFT）、偏好优化（DPO、ORPO）和强化学习（GRPO、GSPO、PPO）：Hugging Face TRL、Axolotl、Unsloth、 LLaMA-Factory。这是大多数团队实际接触的层。
  3. 参数高效方法与托管服务。 PEFT 库实现的 LoRA、QLoRA、DoRA，加上完全隐藏加速器的托管微调 API。

有两个 2026 年的主题把这层和全书串起来。一是 FP8 训练已经主流化：Google 的 Ironwood TPU 在矩阵单元里原生支持 FP8，Megatron-Core 提供 FP8 训练，Unsloth 做 FP8 强化学习（Google Cloud, 2026）。二是对一本基础设施的书更要紧的：RL 后训练已把训练和推理服务融合在一起。现代 RL 工具包内嵌一个推理引擎（几乎总是 vLLM）来生成 rollout，于是训练的盒子里就装着一个服务的盒子。这正是本章末尾要讲的接线故事。

第一个岔路：你到底要不要训练？

挑工具之前，先回答更难的问题。在 2026 年，对很多任务而言，诚实的默认是「别训练权重」。提示工程、少样本示例、检索（第 47 章）和结构化输出，已经覆盖了过去人们经常靠微调才能解决的大部分需求。OpenAI 一边收缩自助微调产品，一边引导用户改用提示缓存、更小的基座模型和 RAG（explainx.ai，二手）。

只有当你需要一种上下文窗口无法廉价承载的「持久行为改变」时，才去微调：

  • 提示总是偏离的一致输出格式或固定文风，
  • 基座模型里缺少的某个狭窄领域的词汇或约定，
  • 把大模型的行为蒸馏成一个小型专用模型，换来推理延迟或成本上的收益（这就是下面的约束箭头），
  • 靠强化学习对着一个可验证的奖励塑造出来的能力，即 第 14 章 讲的推理和智能体情形。

如果这些都不成立，就把这一周花在把提示和检索做得更好上，别去跑训练。

约束箭头

服务层向上伸手，支撑起微调最常见的那个理由。一个你已经专化过的小模型，每词元的服务成本远低于 API 背后的大型通用模型（第 44 章）。当你服务量很大，这次训练的成本就会从推理节省里赚回来，这和 第 3 章 里「为推理而过度训练」的逻辑是一回事，只是上移了一层。所以这里的微调，本质上是一个穿着「训练」外衣的「服务成本」决策。

改一改下面这些数字（一次微调成本和两个服务价格，都是示意），看两条成本线在哪里交叉：盈亏平衡点以下，大型 API 模型便宜；以上，微调过的小模型赢。

import numpy as np
import matplotlib.pyplot as plt

# Illustrative only: shape of the trade-off, not a quote.
finetune_cost = 50.0      # one-time fine-tune run, USD
big_price = 5.0           # large API model, USD per 1M tokens served
small_price = 0.5         # fine-tuned small model, USD per 1M tokens served

vol = np.linspace(0, 40, 200)            # millions of tokens served
big_total = big_price * vol              # no training, pay per token
small_total = finetune_cost + small_price * vol

break_even = finetune_cost / (big_price - small_price)
print(f"break-even at {break_even:.1f}M tokens served")

plt.plot(vol, big_total, label="big API model")
plt.plot(vol, small_total, label="fine-tuned small model")
plt.axvline(break_even, ls="--", color="gray")
plt.xlabel("tokens served (millions)"); plt.ylabel("total cost (USD)")
plt.legend(); plt.title("When does a fine-tune pay for itself?")
plt.show()

参数高效方法

这些是技术，不是产品；它们活在 PEFT、Unsloth 和 TRL 里。低秩更新为什么够用，理论见 第 9 章。

  • LoRA。 低秩适配器，默认选。合并进基座权重后，推理没有额外延迟。
  • QLoRA。 4-bit（NF4）冻结基座加 LoRA；约 1K 到 50K 样本时单 GPU 的甜区。
  • DoRA。 权重分解 LoRA（幅度加方向）；收敛更好，数据量大时值得，约 50K 到 500K 样本。
  • rsLoRA。 高秩用的秩稳定 LoRA。
  • 更新的 arXiv 变体（RandLoRA、激活空间方法）有，但还不是默认。视为前沿、生产未验证 （AppScale 2026）。

如何选择

一旦确定真的需要训练权重，四个问题就能定下工具。

运行规模。 一块消费级或单块 GPU 指向 Unsloth，因为它有专用 kernel 和低显存。几块 GPU 加配置即代码指向 Axolotl 或 LLaMA-Factory。多节点预训练或继续预训练指向 TorchTitan/FSDP2、Megatron-Core，或 TPU 上的 MaxText。

你在什么生态里。 NVIDIA GPU 加想要厂商支持，指向 Megatron-Core/NeMo。PyTorch 原生且能改，指向 FSDP2/TorchTitan + TRL。TPU 指向 JAX/MaxText。纯 Hugging Face 肌肉记忆，直接上 TRL。

方法。 文风或格式加小数据指向 QLoRA。更深的领域迁移加更多数据指向 DoRA 或高秩 LoRA。结构性的领域变化加 500K 以上样本指向 全量微调。针对奖励的推理或智能体行为，指向 Unsloth、TRL 或 torchforge 里的 GRPO/GSPO（第 14 章）。

自托管还是托管。 托管赢在首次运行的时间、无需 GPU 运维、弹性成本，以及按训练词元的可预测定价。自托管赢在数据驻留、IP 控制、非常规配方、可摊销硬件的重复或大型运行，以及避免厂商锁定或突然弃用。注意便利税：Together 按训练词元给 LoRA 计费，还要再加一个单独的按小时专用端点来服务结果，所以那个便宜的标价并不是全部账单。

具体怎么选：

  • Unsloth，当你在一块 24 到 80GB GPU 上、要最快最省显存的 SFT 或长上下文 GRPO。
  • Axolotl，当你想要几块 GPU 上可复现的 YAML 配置运行，并且看重 CI 里的配置即代码。
  • LLaMA-Factory，当你需要模型支持的广度，或给非专家用的低代码 UI。
  • TRL，当你在编写自定义后训练逻辑、要权威训练器时直接选它。
  • TorchTitan/FSDP2 或 Megatron-Core，当你在做真正的多节点预训练或继续预训练。
  • MaxText，当你在 TPU 上。
  • 一个托管服务，当你没有 GPU 运维意愿、且是标准的 SFT/LoRA/DPO/RFT 工作负载；但考虑 2026 年的弃用先例，要设计好导出路径。

一个合理的默认（2026 年年中）

对一个已确定真的需要微调开放权重模型的典型产品团队，截至 2026 年 6 月：

默认：在 TRL + PEFT 之上用 Axolotl（YAML 配置）做 QLoRA，跑在租用的 GPU 上（Modal、 Runpod 或你自己的云）。它可复现，配置即代码契合 CI 与评估（第 48 章），QLoRA 让你停在单块或几块 GPU，权重和数据都还在你自己手里。起步配方是 r=16、开启 DoRA、 target_modules="all-linear"，难一点的任务再加秩（AppScale 2026）。

  • 备选 A，最大单 GPU 效率或 RL： Unsloth，尤其适合消费级 GPU 或长上下文 GRPO。
  • 备选 B，完全没有 GPU 运维： 托管服务。Together 用于廉价的开放权重 LoRA/SFT， Fireworks 用于调优与服务合一，Bedrock 用于 AWS 原生。设计好导出和可移植路径；别以为托管 FT 产品会永远存在。OpenAI 在 2026 年 5 月宣布的自助收缩，就是个教训。

如果是多节点预训练而非微调，默认就转向 TorchTitan/FSDP2 或 Megatron-Core，或 TPU 上的 MaxText。

接进技术栈

2026 年最有标志性的接线事实是：RL 后训练如今内嵌了推理层。 一个 GRPO 或 PPO 循环从当前策略生成 rollout，用奖励打分，然后更新权重。生成是瓶颈，工具包就把它交给一个快速推理引擎，几乎都是 vLLM。Unsloth 驱动 vLLM 做 rollout；torchforge 用 vLLM 做生成、TorchTitan 做训练，通过一个 RDMA 张量存储在两者之间搬运权重（PyTorch 博客）。所以你架构图里的训练盒子，里面就装着一个服务盒子。这正是 第 44 章 里那个 vLLM，如今被当作训练的一个子组件来用，恰好印证本书的论点：这些层本是一套基础设施。

有两种架构模式来切分这个循环的算力。同址模式把训练器与 rollout 引擎放在同一批 GPU 上，并在两者之间对模型重新分片：HybridFlow（其开源实现是 veRL）用它所称的 3D-HybridEngine，在训练布局与生成布局之间对 actor 重新分片，并复用训练权重来做生成，于是不重复占用显存 (Sheng et al. 2025)。分离模式则把 actor、reward、reference 与 critic 各模型放到分开的 GPU 池上，用 Ray 来调度：OpenRLHF 走的是这条路，内嵌 vLLM 来承担那个主导了 RLHF 墙钟时间、按它自己的度量约占其八成的 rollout 阶段 (Hu et al. 2024)。这一选择，正是那个熟悉的取舍：为利用率而打包，还是为调度灵活性而分离，如今被搬进了单次训练运行的内部。

更深一层的旋钮，是 rollout 必须有多新鲜。严格的同策略（on-policy）强化学习，在每一批之前都要等最新的权重，于是在较慢的生成器运行时，训练器就闲着。异步强化学习则让生成在略陈旧的权重上跑在前头，把两者重叠起来，以一份受控的异策略（off-policy）陈旧度换取吞吐，这与 第 8 章 的流水线调度在梯度层面所做的陈旧度对利用率的取舍如出一辙。

训练完成后，你合并适配器，或用一个适配器感知的引擎直接服务它，把权重交给网关背后的服务层（第 44 章），并在晋升之前对它跑一遍评估 harness（第 48 章）。检索与 智能体层随后消费这个被服务的模型。适配器感知的服务，也就是一个基座上挂众多 LoRA，正是托管适配器平台历来契合的地方。整个流程汇入 第 49 章 的端到端技术栈。

一份可改写的配置与启动

一份最小的 Axolotl QLoRA 配置，只是示意，拿去改的：

# qlora.yml
base_model: Qwen/Qwen3-8B
load_in_4bit: true          # QLoRA: 4-bit NF4 frozen base
adapter: lora
lora_r: 16
lora_alpha: 32
lora_target_modules: all-linear
datasets:
  - path: ./data/sft.jsonl
    type: chat_template
gradient_checkpointing: true
sequence_len: 4096
micro_batch_size: 2
num_epochs: 3
# distributed backend (FSDP2 or DeepSpeed) configured via accelerate

启动它，然后为服务合并适配器：

# train (single or few GPUs via accelerate)
accelerate launch -m axolotl.cli.train qlora.yml

# merge the LoRA adapter back into the base for adapter-free serving
python -m axolotl.cli.merge_lora qlora.yml --lora_model_dir ./out

合并后的权重再交给服务栈。把配置放进版本控制，让一次训练成为一个可审的 diff，和你对技术栈其余部分的纪律一样。

收束：能力、效率、信任

透过本书的视角，微调首先是一个「能力」杠杆，即提示承载不了的持久行为改变。它也越来越是一个「效率」杠杆，把大模型蒸馏成廉价可服务的小模型，这正是服务成本约束箭头频繁向上指的原因。它还是一个「信任」面：被微调的模型吸收了你的数据，所以数据驻留、可复现的配置即代码、晋升前的评估闸门，都不是锦上添花，而是让你能把权重发出去的那些控制。2026 年诚实的默认，仍然是先去做好提示和检索，只有当行为改变必须活在权重里时，才去训练。
