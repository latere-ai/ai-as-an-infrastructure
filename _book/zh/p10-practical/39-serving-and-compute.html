第十部分 · 实践：搭建 2026 技术栈 · 第 39 章

服务、网关与算力

这是一章动手实践的内容。服务为何困难的理论在 第 16 章 与 第 17 章 里已经讲过，本章只做工具选型。我们会涵盖怎样搭一个自托管端点、何时该转而依赖托管 API、如何在前面架一个网关来管理密钥与成本控制。本章自上而下走三个层级，叠成一条完整的请求路径：你对话的网关、解码 token 的服务引擎，以及下方的 GPU。

截至 2026 年年中下文都是带日期的快照。工具排名、版本号和价格每个季度都在变。基准测试来自第三方博客且与具体负载相关，当作方向性参考而非事实，落地前重新核实。真正持久的是分类、权衡和接线方式，而非任何单一数字。

三层

一个自托管推理栈是三层，外加一条贯穿其中的统一接口。图 39.1 展示了请求路径。

接口是整套设计的关键。到 2026 年，几乎每个引擎和网关都讲 OpenAI 的 HTTP 形态（/v1/chat/completions、/v1/completions、/v1/embeddings）。这一单一约定让你能把自托管模型换成托管模型、在多个引擎前统一架一个网关、让评估框架（第 43 章）指向同一个 URL。围绕它来构建，每一层都保持可替换。

第 1 层：服务引擎

服务引擎把权重变成一项服务：加载模型到加速器、对请求批处理、运行前向、管理键值缓存、流式返回 token。可控成本和用户感知延迟主要都在这一层。同一组权重用两个不同的引擎、或同一引擎的两套配置，每秒 token 数和尾延迟可以差十倍。

两个阶段驱动每一项设计选择（第 16 章）。Prefill 并行处理整个提示词，受计算限制。Decode 每次产一个 token，每一步要重读缓存，受内存带宽限制。真正重要的特性都是对两者权衡的回应：连续批处理（每步加入退出请求，2026 年的基础设施标配）、PagedAttention（缓存存为非连续页，避免碎片化）、前缀缓存 / KV 复用（共享前导前缀只算一次，是智能体和 RAG 的主要收益，SGLang 的 RadixAttention 推广为基数树）、量化（第 19 章：FP8、FP4、AWQ/GPTQ INT4、GGUF K-quants）、投机解码（第 18 章）、结构化输出（XGrammar 的语法约束解码）、prefill/decode 解耦（两个阶段分别用独立的 worker 池，2026 年数据中心的标准做法）。

截至 2026 年年中，二手基准报告 SGLang 在某些 H100 单模型测试上领先 vLLM（有处引用约 29%），在前缀密集流量上优势更明显、到 70B 规模差距缩小；LMDeploy 吞吐接近 SGLang、INT4 70B 的 TTFT 同级最佳；MLX 在某些 Apple Silicon 模型上比 llama.cpp 快 30 到 50%。这些来自厂商与博客基准，随模型、GPU、批形状和调优而变，容易过时。在把任何一处当决胜因素之前，先在自己的负载上验证。

如何选引擎

这个决策主要取决于三件事：你在哪里运行、流量长什么样、能投入多少性能工程。

  • 要 GPU 上稳妥、生态成熟、模型和特性现成丰富，就选 vLLM。这对多数团队是正确答案。
  • 流量前缀密集（智能体、RAG、多轮）或服务大型 MoE，想拿顶级吞吐，就选 SGLang。先在自己的负载上验证收益。
  • 全栈 NVIDIA、延迟和吞吐是一等成本，能在工具链上投入，就选 TensorRT-LLM。
  • 量化的 w4a16 服务和低 TTFT 最关键，就选 LMDeploy。
  • 需要可移植性（CPU、AMD Vulkan/ROCm、Metal）、边缘或本地部署、GGUF 量化，不需要数据中心级并发，就选 llama.cpp。
  • 目标是笔记本或少数内部用户，就选 Ollama 或 MLX；Apple Silicon 上选 MLX 拿最快单流。
  • 已超出单节点、需要跨机群的 KV 感知路由、解耦和 SLO 驱动的自动伸缩，就上 Dynamo 或 llm-d。
  • 2026 年不从 TGI 起步；已归档且仅维护。

稳妥默认（2026 年年中）： vLLM 架在 OpenAI 兼容端点之后，开启前缀缓存，配上合适的量化（Hopper/Blackwell 用 FP8，或用 AWQ/GPTQ INT4 把更大模型塞进更小卡），并为任何工具调用或抽取路径配 XGrammar 支持的结构化输出。覆盖最广、最不后悔的选择。本地和开发用 Linux/Windows 的 Ollama 或 llama.cpp、macOS 的 MLX。它们是单节点、低并发工具；不要在高流量路径上用它们。

一个最小的单节点 vLLM 启动：

vllm serve <model-id> \
  --enable-prefix-caching \
  --quantization fp8 \
  --guided-decoding-backend xgrammar
# 在 :8000 暴露一个 OpenAI 兼容服务器

标志名与结构化输出参数在 vLLM 各版本间会漂移；请查阅你所用版本的文档。

第 2 层：网关

模型网关是位于应用代码与众多模型供应商之间的控制平面。最单薄的描述是一个反向代理，讲一套 API，把请求扇出到 OpenAI、Anthropic、Google、Bedrock、Azure、自托管的 vLLM 和 OpenRouter 这样的聚合器。但这只是表面。网关真正做的，是把五件没人愿意散落在应用代码里的事集中起来：

  1. 统一 API。 一套请求 schema，把 gpt-5 换成 claude-opus-4 或自托管变体，改改配置就行，不用改代码。
  2. 密钥托管。 供应商密钥留在服务器。应用和智能体只持有短期的虚拟密钥，受模型白名单和预算限制，永远不接触原始凭据。
  3. 成本追踪。 按密钥、按团队、按标签的花费，归因并可导出。这是团队采用网关最常引的理由。
  4. 回退与路由。 重试、供应商故障切换、负载均衡、上下文窗口回退、按成本或延迟的智能选择。
  5. 预算与策略。 硬性花费上限、速率限制、护栏（PII 脱敏、越狱过滤）和审计轨迹。

网关是服务层与上面一切之间的缝。最新的网关把这一理念从单纯的 LLM 调用扩展到智能体原生协议（工具用 MCP、智能体间用 A2A），于是网关也成了工具和智能体流量的策略点。这直接连到 第 41 章 的运行框架工作和 第 34 章 的权限管制。

若干厂商发布了夸张的开销数字（Bifrost「比 LiteLLM 快 50 倍」和「约 11µs」；Portkey「<1ms」；LiteLLM「1k RPS 下约 8ms P95」）。这些是条件不一致的厂商基准、未经独立验证。持久的要点是：编译语言网关（Go/Rust：Bifrost、agentgateway、Helicone、Envoy）通常宣称比 Python 的 LiteLLM 代理开销低，但对多数负载，供应商和模型延迟以数量级压过网关开销。在把开销当决胜因素之前，先在自己流量上做基准。

如何选网关

按顺序处理两个轴：托管对自托管，再是纯 LLM 对智能体原生。

  • 独立开发者或小团队、想要最大目录、零基础设施、零合同，就选 OpenRouter。
  • 想要自托管、广泛兼容、且有 DevOps 能力去运行，尤其在 Python 栈，就选 LiteLLM。
  • 治理、护栏和合规是硬要求，就选 Portkey；如果已在运行 Kong，就选 Kong。
  • 路线图偏智能体、需要把 LLM、MCP 和 A2A 流量纳入一个受治理的策略点，就选 agentgateway。
  • 平台团队已身处 Envoy/Istio/Gateway API、想让 AI 控制平面留在同一套 CRD，就选 Envoy AI Gateway。
  • 想要零基础设施、接受密钥和请求元数据走过第三方，就用托管网关（OpenRouter、Cloudflare、Portkey 托管版）。当密钥托管、审计或合规逼你时，再转向自托管。

稳妥默认（2026 年年中）： 自托管 LiteLLM 作网关，搭配一层可观测性（Helicone 或 LiteLLM 仪表盘）做花费和请求分析。最广的供应商覆盖、带预算的虚拟密钥、花费追踪和回退、全部开源、在自己环境里、生态几乎一切都互通。若路线图偏智能体，尽早评估 agentgateway，让 LLM、工具和智能体流量共享一个策略点，省得日后再把智能体的事硬接到只懂聊天的代理上。

披露：作者自己的栈用 Lux 作网关。它在此作为这些模式的样例出现，而非相对上述选项的中立推荐。

一个最小的 LiteLLM 配置，把一个托管模型与一个自托管模型统一到一个名字之后，并加上回退：

model_list:
  - model_name: smart            # 你的应用请求的名字
    litellm_params:
      model: anthropic/claude-opus-4
      api_key: os.environ/ANTHROPIC_API_KEY
  - model_name: smart            # 同一别名，负载均衡 / 回退目标
    litellm_params:
      model: openai/gpt-5
      api_key: os.environ/OPENAI_API_KEY
  - model_name: local
    litellm_params:
      model: openai/<model-id>   # 你的 vLLM，OpenAI 兼容
      api_base: http://vllm-svc:8000/v1

litellm_settings:
  fallbacks: [{ "smart": ["local"] }]   # 若托管 "smart" 失败，用 local
  num_retries: 2

# 虚拟密钥、团队预算与花费上限经由
# /key/generate API 与代理 UI 签发，而非此文件。

应用把一个标准 OpenAI 客户端指向该代理、请求模型 "smart"。网关解析别名、做负载均衡或故障切换、把花费记到虚拟密钥、发出追踪。上游的 "local" 解析到第 1 层引擎，于是自托管和托管模型在一个名字之后可互换：

from openai import OpenAI
client = OpenAI(base_url="https://gateway.internal/v1", api_key="<virtual-key>")
resp = client.chat.completions.create(
    model="smart",
    messages=[{"role": "user", "content": "..."}],
)

schema 在 LiteLLM 各版本间会漂移；确切的键请查阅文档。

第 3 层：其下的算力

上面的一切最终都落到 GPU 上，需要有人去预置、调度、付费。两个问题居中、大体正交：GPU 从哪来（自建对租用轴）以及怎样调度。硬件本身见 第 30 章；编排基底见 第 31 章；成本算术见 第 37 章。这里我们做选择。

自托管对调用 API

为 GPU 定容之前，先解决前置问题：要不要自托管？多数团队应从托管 API 起步、仅当具体压力逼迫时才自托管。这个决策的核心考量是：

  • 流量突发或低量、想要前沿模型但不想运维、上线速度比 token 成本重要、数据可以离开环境，就调用托管 API（通过网关）。这是多数应用团队的正确选择。
  • 持续高利用率使 token 经济性占主导、数据驻留或合规要求权重和提示留在环境、需要某个 API 不提供的开放权重模型或微调、或需要 API 给不了的延迟和尾部行为控制，就自托管。

网关让这件事可逆。两条路都讲同一种 OpenAI 形态的接口，可以从托管起步、把自托管路由作为又一个别名加进来、改配置就能迁移流量。模型选择见 第 38 章；栈的接线见 第 44 章。

GPU 从哪里来

一条谱系从无服务器 GPU 平台（推函数或模型、机器由它们管）、经租用 GPU 云和 neocloud、到超大规模云、再到 colo 里自有硬件。决定性变量是持续利用率。

层级 例子 计费形态 最适合
无服务器 GPU / 托管推理 Modal、Replicate、Baseten、RunPod Serverless、Fireworks、Together 按秒 / 按 token，可缩容到零 突发或低利用率推理，零基础设施运维
GPU 云 / neocloud CoreWeave、Lambda、Nebius、Crusoe 按需 + 预留 GPU 小时 稳定、高利用率的训练和服务集群
市场 / spot Vast.ai、去中心化 按小时，可中断 最便宜的容错批处理；绝不用于延迟敏感服务
超大规模云 AWS、GCP、Azure 按需 / 预留；自研芯片 已在其上、菜单最广、托管流水线、TPU/Trainium
自有硬件（colo） 自运维 资本支出 + 运维 规模化的持续极高利用率，且具备运维能力

定价波动、聚合器之间不一致，因此锚定形态而非美元数字。截至 2026 年年中，标价锚把无服务器 H100 定在每小时 3 到 4 美元左右（Modal 约 3.95/hr、RunPod 约 2.89/hr），各层级 H100 按需价大约有 5 倍跨度。落地前重新核实；这些每季度都在动。

经验法则：低于专用 GPU 持续利用率约 40 到 50% 时，无服务器更便宜，因为空闲时不付钱。高于此点，neocloud 或超大规模云的预留 GPU 小时价会同时压过无服务器和按需。仅在持续极高利用率、摊销后资本支出胜过多年租金时才自有硬件。仅为容错批处理用市场或 spot。想保持可移植、跨云追逐最便宜可用容量、避免锁定时，在所有这些之上用 SkyPilot。

改改这两个每小时价、看无服务器和预留的成本线在哪里相交；用本章的标价锚、盈亏平衡点落在所说的 40 到 50% 区间附近。

import numpy as np, matplotlib.pyplot as plt
serverless_rate = 3.95   # $/GPU-hour, pay only when busy (scale-to-zero)
reserved_rate   = 2.00   # $/GPU-hour, billed 24/7 whether idle or not
hours = 730              # one month
u = np.linspace(0, 1, 101)
serverless = u * hours * serverless_rate      # cost scales with utilization
reserved   = np.full_like(u, hours * reserved_rate)  # flat cost
breakeven = reserved_rate / serverless_rate   # crossover utilization
print(f"break-even utilization: {breakeven*100:.1f}%")
plt.plot(u*100, serverless, label="serverless (pay-per-use)")
plt.plot(u*100, reserved, label="reserved (flat)")
plt.axvline(breakeven*100, ls="--", color="gray")
plt.xlabel("sustained utilization (%)"); plt.ylabel("monthly cost ($)")
plt.legend(); plt.title("GPU cost: serverless vs reserved"); plt.show()

GPU 如何被调度

掌控一个资源池后、由控制平面决定放置。三个主导者及其分工：

  • Slurm，主导负载是大型多节点训练和批处理（启动、跑数小时、检查点、退出）。gang 调度原生且简单。代价是没有原生的服务、入口或自动伸缩。
  • Kubernetes，运行推理服务、混合负载或微服务、想要自动伸缩、入口和服务网格。加 Volcano 或 NVIDIA KAI Scheduler 做 gang 调度、加 Kueue 做多团队配额和准入、加 DRA 做细粒度 GPU/MIG 分配。
  • Ray（在 KubeRay 上），团队是 Python 原生、想在一个框架里同时做分布式训练、RL、数据和服务、运行在 K8s 上。

大团队常见的分工是训练用 Slurm、服务用 Kubernetes。2026 年的收敛是 Slurm-on-K8s 项目（SchedMD Slinky、CoreWeave SUNK、Nebius Soperator）在共享 K8s 基础设施上保留 Slurm 的 gang 语义、缩小这道分工。势头朝着即便训练也标准化到 Kubernetes（通过上述插件），因为如今主导 AI 算力开销的是推理而非训练，而服务恰好要 Kubernetes 那种弹性、缩容到零、延迟感知的调度。

稳妥默认（2026 年年中）： 对一个交付 AI 功能、混合突发推理和偶尔微调、没有专职基础设施团队的团队，从无服务器 GPU 或托管推理起步（Modal 拿通用无服务器 Python 工效、Baseten 拿带 SLA 的生产服务、Fireworks 或 Together 拿纯开放权重的 token 推理）。当利用率攀升、租金溢价开始主导账单时，升级到用 Slurm 训练、Kubernetes 服务来调度的预留 neocloud 集群。

约束箭头一个 token 的服务成本定在这一层，却一路向上回到预训练。@sec-scaling-laws 把一个更小的模型训练到超过 Chinchilla 最优，正是因为这里定下的 GPU 小时和 token 经济性，要为模型的整个服务生命周期买单。栈底部的一个选择，定了栈顶的一个参数。

接线到一起

三层组合成一条请求路径（图 39.2），OpenAI 兼容接口正是让每一层保持可替换的东西。

三个事实让这套在实践中成立。应用从不持有供应商密钥：它们持有网关签发的虚拟密钥，于是轮换凭据或给失控智能体封顶是服务端操作、无需客户端重新部署。一个 base URL、OpenAI 形态、同样服务应用代码、评估框架和智能体运行时，切换模型或加回退就是改改配置。由引擎、不是提示词来强制结构化输出：下游代码解析工具调用或抽取数据时，XGrammar 的引导解码是可靠的路。

能力、效率、信任

三棱镜的收尾把各层连回本书的主线。能力是网关的触达：一套接口让每个模型（托管或自托管）都可寻址，为每次调用挑最佳模型成了一条路由规则。效率是引擎和算力层的协同：连续批处理、前缀缓存和量化抬高每秒 token 数，自建对租用和利用率的决策为每个 token 设下美元底线。信任又是网关作为策略点：密钥托管、花费上限、审计、PII 脱敏，以及把工具和智能体流量纳入一个受治理之缝的智能体原生协议，这正是本章交棒给 第 34 章 的地方。
