服务、网关与算力

这是一章动手实践的内容。服务为何困难，理论在 第 16 章 与 第 17 章 里已经讲过，本章只做工具选型。读完之后，你应该能搭起一个自托管端点，也知道什么时候不该这么做；能在它前面架一个网关来管理密钥与成本；还能把整套东西放到自己真正付得起的算力上。本章自上而下走三个层级，它们叠成一条完整的请求路径：你对话的网关、解码 token 的服务引擎，以及下方的 GPU。

截至 2026 年年中下文都是带日期的快照。工具排名、版本号和价格每个季度都在变。基准测试来自第三方博客，且与具体负载相关，当作方向性参考而非事实，落地前请重新核实。真正持久的是分类、权衡和接线方式，而非任何单一数字。

三层

一个自托管推理栈就是三层，外加一条贯穿其中的统一接口。图 39.1 展示了请求路径。

接口是整套设计的关键。到 2026 年，几乎每个引擎和网关都讲 OpenAI 的 HTTP 形态（/v1/chat/completions、/v1/completions、/v1/embeddings）。正是这一单一约定，让你能把自托管模型换成托管模型，能在多个引擎前统一架一个网关，也能让评估框架（第 43 章）指向和生产同一个 URL。围绕它来构建，每一层就都保持可替换。

第 1 层：服务引擎

服务引擎把一组权重变成一项服务：加载模型到加速器、对请求批处理、运行前向、管理键值缓存、流式返回 token。可控成本和用户感知到的延迟，主要都落在这一层。同一组权重换两个不同的引擎，或同一引擎换两套配置，每秒 token 数和尾延迟可以差出一个数量级。

有两个阶段驱动着每一项设计选择（第 16 章）。Prefill 并行处理整个提示词，受计算限制。Decode 每次产出一个 token，每一步都要重读缓存，受内存带宽限制。真正重要的那些特性，都是对这两者之间张力的回应：连续批处理（每一步都加入和退出请求，到 2026 年已是基础设施标配）、PagedAttention（缓存存为非连续的页，内存不再碎片化）、前缀缓存 / KV 复用（共享的前导前缀只算一次，这是智能体和 RAG 的主要收益，被 SGLang 的 RadixAttention 推广为一棵基数树）、量化（第 19 章：FP8、FP4，经 AWQ/GPTQ 的 INT4，GGUF K-quants）、投机解码（第 18 章）、结构化输出（经 XGrammar 的语法约束解码），以及 prefill/decode 解耦（两个阶段各用一组独立的 worker 池，这是 2026 年数据中心的招牌做法）。

截至 2026 年年中，二手基准报告称 SGLang 在某些 H100 单模型测试上领先 vLLM（有处引用约 29%），在前缀密集的形态上优势更大，到 70B 规模差距收窄；LMDeploy 吞吐接近 SGLang，而 INT4 70B 的 TTFT 同级最佳；MLX 在某些 Apple Silicon 模型上比 llama.cpp 快 30 到 50%。这些都出自厂商和博客的基准，随模型、GPU、批形状和调优而变，而且过时很快。在把其中任何一项当成决胜因素之前，先在自己的负载上验证。

如何选引擎

这个决策主要取决于三件事：你在哪里运行、流量长什么样、能投入多少性能工程。

  • 要在 GPU 上有一个稳妥、广受支持的默认，要现成的宽模型和特性覆盖，且看重生态成熟度胜过最后那 20% 的性能，就选 vLLM。对多数团队，这就是正确答案。
  • 流量前缀密集（智能体、RAG、多轮），或者服务大型 MoE 模型，想在这些形态上拿到顶级吞吐，就选 SGLang。先在自己的流量上验证这份收益。
  • 全栈 NVIDIA，延迟和吞吐是一等成本，且能在工具链上投入，就选 TensorRT-LLM（默认的 PyTorch 后端把这份成本降到了比旧构建流程更低）。
  • 量化的 w4a16 服务和 NVIDIA 机群上的低 TTFT 最要紧，就选 LMDeploy。
  • 需要可移植性（CPU、经 Vulkan/ROCm 的 AMD、Metal）、边缘或本地部署、GGUF 量化，又不需要数据中心级的并发，就选 llama.cpp。
  • 目标是一台笔记本或少数几个内部用户，就选 Ollama 或 MLX；在 Apple Silicon 上专门选 MLX，拿最快的单流。
  • 已经长出了单节点的规模，需要跨机群的 KV 感知路由、解耦和 SLO 驱动的自动伸缩，就上 Dynamo 或 llm-d。
  • 2026 年别从 TGI 起步；它已归档，只剩维护。

稳妥的默认（2026 年年中）： vLLM 架在一个 OpenAI 兼容端点之后，开启前缀缓存，配上合适的量化（Hopper/Blackwell 用 FP8，或用 AWQ/GPTQ 的 INT4 把更大的模型塞进更小的卡），再给任何工具调用或抽取路径配上 XGrammar 支持的结构化输出。这是覆盖最广、最不后悔的选择。本地和开发场景下，默认翻转成 Linux/Windows 上的 Ollama 或 llama.cpp、Mac 上的 MLX。它们是单节点、低并发的工具；别把它们提拔到高流量路径上。

一个最小的单节点 vLLM 启动：

vllm serve <model-id> \
  --enable-prefix-caching \
  --quantization fp8 \
  --guided-decoding-backend xgrammar
# 在 :8000 暴露一个 OpenAI 兼容服务器

标志名和结构化输出参数在 vLLM 各版本间会漂移；请查阅你所用版本的文档。

第 2 层：网关

模型网关是位于你的应用代码与它对话的众多模型供应商之间的控制平面。说得最单薄一点，它就是个反向代理，讲一套 API，把请求扇出到 OpenAI、Anthropic、Google、Bedrock、Azure、你自己的 vLLM，以及 OpenRouter 这类聚合器。但这低估了它。网关真正做的，是把五件没人愿意散落在应用代码里的事集中起来：

  1. 统一 API。 一套请求 schema，于是把 gpt-5 换成 claude-opus-4 或一个自托管变体，改改配置就行，不必改代码。
  2. 密钥托管。 供应商密钥留在服务器上。应用和智能体只持有短期的虚拟密钥，受限于一份模型白名单和一份预算，永远不碰原始的供应商凭据。
  3. 成本追踪。 按密钥、按团队、按标签的花费，已归因且可导出。这是团队采用网关时最常被引用的理由。
  4. 回退与路由。 重试、供应商故障切换、负载均衡、上下文窗口回退、按成本或延迟来选模型。
  5. 预算与策略。 硬性的花费上限、速率限制、护栏（PII 脱敏、越狱过滤），以及一条审计轨迹。

网关是服务层与它上面一切之间的那道缝。最新的网关把这一理念从单纯的 LLM 调用，延伸进了智能体原生协议（工具用 MCP、智能体之间用 A2A），于是网关也成了工具和智能体流量的策略点。这一点直接连到 第 41 章 的运行框架工作，以及 第 34 章 的授权模型。

有几家厂商发布了夸张的开销数字（Bifrost「比 LiteLLM 快 50 倍」和「约 11µs」；Portkey「<1ms」；LiteLLM「1k RPS 下约 8ms P95」）。这些都是条件不一致的厂商基准，未经独立验证。持久的要点是：编译型语言写的网关（Go/Rust：Bifrost、agentgateway、Helicone、Envoy）通常宣称比 Python 的 LiteLLM 代理开销更低，但对多数负载，供应商和模型的延迟以数量级压过网关开销。在把开销当成决胜因素之前，先在自己的流量上做基准。

如何选网关

按顺序走两条轴：先是托管对自托管，再是纯 LLM 对智能体原生。

  • 你是独立开发者或小团队，想要最大的目录、零基础设施、零合同，就选 OpenRouter。
  • 想要一个自托管、广泛兼容的网关，且有 DevOps 能力去运行它，尤其在 Python 栈上，就选 LiteLLM。
  • 治理、护栏和合规是硬要求而非锦上添花，就选 Portkey；要是已经在跑 Kong，就选 Kong。
  • 路线图偏智能体，需要把 LLM、MCP 和 A2A 流量纳入一个受治理的策略点，就选 agentgateway。
  • 平台团队本就活在 Envoy/Istio/Gateway API 里，想让 AI 控制平面留在同一套 CRD 中，就选 Envoy AI Gateway。
  • 想要零基础设施，且接受密钥和请求元数据要经过一个第三方，就用托管网关（OpenRouter、Cloudflare、Portkey 的托管版）。当密钥托管、审计或合规逼你时，再转向自托管。

稳妥的默认（2026 年年中）： 自托管 LiteLLM 作网关，再配一层可观测性（Helicone 或 LiteLLM 自带的仪表盘）来做花费和请求分析。它给你最广的供应商覆盖、带预算的虚拟密钥、花费追踪和回退，全部开源、就在你自己的环境里，而且生态里几乎其他一切都和它互通。若你的路线图偏重智能体，尽早评估 agentgateway，让 LLM、工具和智能体流量共享一个策略点，省得日后再把智能体那摊事硬接到一个只懂聊天的代理上。

披露：作者自己的栈用 Lux 作网关。它出现在这里，是作为这些模式的一个实做样例，而不是相对上述各选项的中立推荐。

一个最小的 LiteLLM 配置，把一个托管模型和一个自托管模型统一到同一个名字之后，并加上一个回退：

model_list:
  - model_name: smart            # 你的应用请求的名字
    litellm_params:
      model: anthropic/claude-opus-4
      api_key: os.environ/ANTHROPIC_API_KEY
  - model_name: smart            # 同一别名，负载均衡 / 回退目标
    litellm_params:
      model: openai/gpt-5
      api_key: os.environ/OPENAI_API_KEY
  - model_name: local
    litellm_params:
      model: openai/<model-id>   # 你的 vLLM，OpenAI 兼容
      api_base: http://vllm-svc:8000/v1

litellm_settings:
  fallbacks: [{ "smart": ["local"] }]   # 若托管 "smart" 失败，用 local
  num_retries: 2

# 虚拟密钥、团队预算与花费上限经由
# /key/generate API 与代理 UI 签发，而非此文件。

随后应用把一个标准 OpenAI 客户端指向该代理、请求模型 "smart"。网关解析别名、做负载均衡或故障切换、把花费记到那把虚拟密钥上、发出追踪。上游处，"local" 解析到你的第 1 层引擎，于是自托管和托管模型在同一个名字之后变得可互换：

from openai import OpenAI
client = OpenAI(base_url="https://gateway.internal/v1", api_key="<virtual-key>")
resp = client.chat.completions.create(
    model="smart",
    messages=[{"role": "user", "content": "..."}],
)

schema 在 LiteLLM 各版本间会漂移；确切的键请查阅文档。

第 3 层：其下的算力

上面的一切，最终都落到某块 GPU 上，要有人去预置、调度、付费。两个问题居于中心，而且大体正交：GPU 从哪来（自建对租用这条轴），以及它们怎样被调度。硬件本身见 第 30 章；编排基底见 第 31 章；成本算术见 第 37 章。这里我们做选择。

自托管对调用 API

为 GPU 定容之前，先解决那个前置问题：到底要不要自托管？多数团队都应当从托管 API 起步，只在某个具体压力逼迫时才自托管。诚实的决策规则是：

  • 流量突发或低量、想要前沿模型但不想运维它、上线速度比每 token 成本更重要、你的数据可以离开你的环境，就（通过网关）调用托管 API。对多数应用团队，这是正确的默认。
  • 以下至少有一条成立，就自托管：持续的高利用率让每 token 经济性占了主导（你能让硬件一直忙着），数据驻留或合规要求权重和提示留在你的环境里，你需要某个 API 不提供的开放权重模型或微调，或者你需要 API 给不了的延迟和尾部行为控制。

网关让这件事可逆。因为两条路都讲同一种 OpenAI 形态的接口，你可以从托管起步，把一条自托管路由当成又一个别名加进来，再改改配置就迁移流量。为任一条路选模型见 第 38 章；整套栈的接线见 第 44 章。

GPU 从哪里来

一条谱系从无服务器 GPU 平台（推上去一个函数或一个模型，机器由它们管），经租用的 GPU 云和 neocloud，到超大规模云，再到 colo 里自有的硬件。决定性的变量是持续利用率。

层级 例子 计费形态 最适合
无服务器 GPU / 托管推理 Modal、Replicate、Baseten、RunPod Serverless、Fireworks、Together 按秒 / 按 token，可缩容到零 突发或低利用率的推理，零基础设施要运维
GPU 云 / neocloud CoreWeave、Lambda、Nebius、Crusoe 按需 + 预留 GPU 小时 稳定、高利用率的训练和服务集群
市场 / spot Vast.ai、去中心化 按小时，可中断 最便宜的容错批处理；绝不用于延迟敏感的服务
超大规模云 AWS、GCP、Azure 按需 / 预留；自研芯片 本就在其上、菜单最广、托管流水线、TPU/Trainium
自有硬件（colo） 自运维 资本支出 + 运维 规模化的持续极高利用率，且有运维实力

定价波动剧烈，聚合器之间也对不上，所以锚定形态，别锚定美元数字。截至 2026 年年中，标价锚把无服务器 H100 定在每小时 3 到 4 美元左右（Modal 约 3.95/hr、RunPod 约 2.89/hr），各层级之间 H100 的按需价大约有 5 倍的跨度。落地前重新核实；这些每季度都在动。

经验法则是：在专用 GPU 的持续利用率低于约 40 到 50% 时，无服务器更便宜，因为空闲时你什么都不付。高于这个点，neocloud 或超大规模云的预留 GPU 小时价会同时压过无服务器和按需。只在持续极高利用率、摊销后的资本支出胜过多年租金时，才自有硬件。市场或 spot 只用于容错的批处理。想保持可移植、跨云追逐最便宜的可用容量、避开锁定时，在所有这些之上用 SkyPilot。

改一改这两个每小时价，看无服务器和预留两条成本线在哪里相交；用本章的标价锚，盈亏平衡点会落在所说的 40 到 50% 区间附近。

import numpy as np, matplotlib.pyplot as plt
serverless_rate = 3.95   # $/GPU-hour, pay only when busy (scale-to-zero)
reserved_rate   = 2.00   # $/GPU-hour, billed 24/7 whether idle or not
hours = 730              # one month
u = np.linspace(0, 1, 101)
serverless = u * hours * serverless_rate      # cost scales with utilization
reserved   = np.full_like(u, hours * reserved_rate)  # flat cost
breakeven = reserved_rate / serverless_rate   # crossover utilization
print(f"break-even utilization: {breakeven*100:.1f}%")
plt.plot(u*100, serverless, label="serverless (pay-per-use)")
plt.plot(u*100, reserved, label="reserved (flat)")
plt.axvline(breakeven*100, ls="--", color="gray")
plt.xlabel("sustained utilization (%)"); plt.ylabel("monthly cost ($)")
plt.legend(); plt.title("GPU cost: serverless vs reserved"); plt.show()

GPU 如何被调度

一旦你掌控了一个资源池，就由一个控制平面来决定放置。三个主导者，以及它们如何分工：

  • Slurm，当主导负载是大型多节点训练和批处理：那些启动、跑上几小时、检查点、退出的作业。gang 调度是原生的，也简单。代价是没有原生的服务、入口或自动伸缩。
  • Kubernetes，当你在跑推理服务、混合负载，或者 AI 旁边还摆着微服务，想要自动伸缩、入口和服务网格那套生态。加 Volcano 或 NVIDIA KAI Scheduler 做 gang 调度，加 Kueue 做多团队的配额和准入，加 DRA 做细粒度的 GPU/MIG 分配。
  • Ray（在 KubeRay 上），当你的团队是 Python 原生，想在一个框架里同时做分布式训练、RL、数据和服务，并骑在 K8s 之上。

大团队常见的分工，是训练用 Slurm、服务用 Kubernetes。2026 年的收敛，是 Slurm-on-K8s 这类项目（SchedMD Slinky、CoreWeave SUNK、Nebius Soperator），在共享的 K8s 基础设施上保留 Slurm 的 gang 语义，把这道分工收窄。势头朝着即便训练也标准化到 Kubernetes（通过上述那些插件），因为如今主导 AI 算力开销的是推理而非训练，而服务恰好要的，正是 Kubernetes 提供的那种弹性、缩容到零、延迟感知的调度。

稳妥的默认（2026 年年中）： 对一个交付 AI 功能、混着突发推理和偶尔微调、又没有专职基础设施团队的团队，从无服务器 GPU 或托管推理平台起步（Modal 拿通用无服务器的 Python 工效，Baseten 拿带 SLA 的生产服务，Fireworks 或 Together 拿纯开放模型的 token 推理）。当利用率攀升、租金溢价开始主导账单时，再升级到用 Slurm 训练、Kubernetes 服务来调度的预留 neocloud 集群。

约束箭头一个 token 的服务成本，定在这一层，却一路向上回到了预训练。@sec-scaling-laws 把一个更小的模型训练到超过 Chinchilla 最优，恰恰是因为这里定下的 GPU 小时和每 token 经济性，要为这个模型的整个服务生命周期买单。栈底的一个参数，定了栈顶的一个选择。

接线到一起

三层组合成一条请求路径，如 图 39.2 所示，而 OpenAI 兼容接口正是让每一层保持可替换的东西。

有三个事实，让这套在实践中立得住。应用从不持有供应商密钥：它们持有的是网关签发的虚拟密钥，于是轮换一个凭据、或给一个失控的智能体封顶，都是服务端操作，无需客户端重新部署。一个 base URL、OpenAI 形态，同样服务于应用代码、评估框架和智能体运行时，于是切换模型或加一个回退就是配置的事。还有，强制结构化输出的是引擎，不是提示词：当下游代码要解析工具调用或抽取的数据时，经 XGrammar 的引导解码是那条可靠的路。

能力、效率、信任

这三棱镜的收尾，把各层连回本书的主线。能力是网关的触达：一套接口让每个模型，无论托管还是自托管，都变得可寻址，于是为每次调用挑最佳模型，成了一条路由规则。效率是引擎和算力层一起协同：连续批处理、前缀缓存和量化抬高每秒 token 数，而自建对租用、利用率的决策，为每个 token 设下了那条美元底线。信任又一次落在网关这个策略点上：密钥托管、花费上限、审计、PII 脱敏，以及那些把工具和智能体流量纳入同一道受治理之缝的智能体原生协议，这正是本章交棒给 第 34 章 那份安全与授权工作的地方。
