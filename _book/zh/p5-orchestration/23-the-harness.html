运行支架

运行支架是模型周围的脚手架，把模型输出转成工具调用、把工具结果转回模型输入，还要管上下文窗口、路由工具、沙箱化执行。它暴露了一些动词让人能暂停、重定向、分叉或杀死一个运行中的循环。一个流程图上再简单不过的循环，到生产就需要这么多机制托着。这套机制的形状对评估分数的影响，不亚于模型本身。

一个不肯保持简单的循环

契约很小：创建一个会话，绑定到一份智能体定义。驱动它的循环，把上下文送给模型，分发返回的工具调用，把结果追加回去，一直重复到完成或中断。支持崩溃或等待后恢复，支持中途打断，支持在某个检查点分叉。画成流程图，就是方框加回边。

一旦进生产，问题就来了。工具跨回合握着连接，循环不再无状态。上下文窗口填满了，得决定遗忘什么。用户在沙箱命令执行到一半时按取消，得停掉它不直接控制的工作。两个副本都盯上同一个滴答，得与看不见的副本协调。运行支架就是这些摩擦被吸收还是露出的地方。

它管的是机制，不是策略。不决定谁能调（那是身份，见 第 34 章）、模型从哪来、哪些动作要人批准（那是监督，见 第 33 章）。它决定这些决策怎么被执行，最关键的机制是停循环的能力。

图 23.1 把这些生产摩擦映射到循环的各处，浓缩了本章的论点：四个看似无关的问题落在一个看起来没有落点的结构上的四个不同地方。

接下来拆解吸收这些摩擦的六个机制。每个都从朴素版本开始，在某个负载点崩掉，然后才长出那个点所需的具体机制。这六个合起来就是运行支架：实例从哪来，取消怎么抵达工作，谁被允许跑，锁保护什么，填满的窗口里什么活下来，模型怎么得知工具存在。每个都有演化历程和权衡的拐点，最后讲循环怎么在无人值守的长夜活下来。

实例从哪里来

第一个决定是何时把智能体定义（提示、工具、模型绑定）变成活的实例。最显然的起点是单例，一个运行器在所有会话间共享，仅用 session_id 隔离，每次请求零分配。隐藏代价不是性能，而是发布粒度。

用单例，提示词就是部署期常量。坏提示会拖垮 100% 会话直到回滚完。OpenAI 的 GPT-4o 谄媚事件就是这样：4 月 25 日上线，4 月 28 日开始回滚，花了大约一天 (OpenAI 2025)。

改用运行时注册表，每次请求解析一个提示版本。回归只触及金丝雀切片，稳定版本继续服务其余的人。爆炸半径从整个机队缩到金丝雀。代价是多一次解析跳转、跨副本的一致性、每次事故多一个变量。

拐点在何时不再可选。单例在一两个智能体类型没问题，过了三四个就开始咬人。一个智能体的提示回归会逼出回滚，把另一个智能体的无关修复也撤销，因为共享部署。这种共享部署的事故，就是版本化从锦上添花变成必需的时刻，因为不做它的代价，成了没人动过的代码里的一次回归。

取消如何抵达工作

取消的效力等于它最盲目那跳的效力。运行支架可以即刻看见中断标志，但标志必须一路向下传到每个可能执行中的层：模型调用遵守上下文截止，工具分发层传播取消到工具，沙箱命令尊重 SIGTERM，有状态协议调用尊重 RPC 级取消。无视截止的模型调用会在取消后继续占会话数十秒。无视 SIGTERM 的沙箱命令会占满整个宽限期。

「运行时支持取消」实际上是关于级联中每一跳的说法。单一个不配合的层就能让取消形同虚设。这就是为什么中断是原语而非特性：人在回路审批所依赖的暂停，必须穿过每一跳，否则就是作戏。

哪些动作需要审批是监督的决定。让审批得以发生的暂停，是运行时的动词。把它作为一等中断暴露出来的框架，让暂停变得可检视而非隐式 (LangChain 2025)。图 23.2 追踪了这条级联及每个不配合跳添加的延迟，「取消只与最盲目的跳一样真实」从断言变成了链的性质。

把某一跳的 obeys 设成 False，看停止耗时如何跳到那一跳的宽限期：取消只能和最盲目的那层一样快。

# Each hop either obeys the interrupt fast, or ignores it and only
# stops when its own grace period expires. Time-to-stop is the slowest hop.
hops = [
    {"name": "model call",   "obeys": True,  "grace_s": 30.0},
    {"name": "tool dispatch","obeys": True,  "grace_s": 5.0},
    {"name": "sandbox cmd",   "obeys": False, "grace_s": 10.0},  # ignores SIGTERM
    {"name": "RPC call",      "obeys": True,  "grace_s": 8.0},
]
flag_latency = 0.01  # harness sets the interrupt flag almost instantly
stop_times = [flag_latency if h["obeys"] else h["grace_s"] for h in hops]
for h, t in zip(hops, stop_times):
    print(f"{h['name']:14s} stops after {t:6.2f}s")
print(f"\ntime-to-stop = max = {max(stop_times):.2f}s "
      f"(bounded by the most-blind hop)")

这动词有四种形状，人的控制质量受限于运行支架提供哪一种。硬取消是 kill(session)，不保留状态，简单粗暴，每次纠正都丢上下文。协作式暂停在步边界检查中断标志并序列化状态。队列式引导把用户输入追加到下一回合不暂停，很快但可能在看见消息前就交付陈旧决定。定点恢复结合引导和回退。审批所依赖的暂停，恰好与运行时实现最强那种一样好，不会更好。

谁被允许运行

循环按调度跑时，每个副本都跑自己的调度器，没协调的话每个都触发每个滴答。通常的修法是在跑前获取智能体级分布式锁，防止两副本并发触发同一滴答。但它不能让滴答的副作用恰好一次。

某个滴答发了 Slack、开了工单，然后在记录「完成」前崩溃。恢复重放它，Slack 消息发了两次。锁协调谁来跑；恰好一次要求协调的是外部世界已经发生了什么。幂等键在副作用调用点弥合这道缝，这是另一种保证，仅靠锁的调度器没有。

锁防的是重叠不是重复。还有第二种、更尖锐的高度错位。运行支架几乎总有会话级锁，阻止两个 Run() 调用同时改一会话。但同一智能体的两个不同会话触碰同一外部资源，它什么都没说。

两个编程会话向同一分支推送冲突的提交。用户会话和被调度的滴答指向同一外部状态，彼此不知道对方。锁在运行支架里，冲突在资源处，运行支架的锁够不着。图 23.3 直接展示了这种错位。

绿色会话各自锁着，红色资源没锁。修法在资源处：每会话一个工作树，把冲突挪到合并里；或按命名资源加资源级锁；或在外部系统乐观调和。这种碰撞不是假想，编程智能体的 PR 里的合并冲突已经频繁到足以构成标注数据集 (Ogenrwot and Businge 2026)。

正确选择取决于下游系统是否有自己的并发控制。Git 引用更新和数据库行锁是真正的协调原语，存在的地方运行支架可以倚靠。

调度器本身也爬同一条压力曲线。进程内和外部 cron 调度器，一旦某个滴答需要多步编排和外部副作用，就让位给持久执行框架（Temporal、Inngest、Restate）。模型行为是概率性的，朴素重试不够，而持久日志正是为此而建的。

会话在滴答间保持持久还是临时，是有自身拐点的平行选择。持久会话累积上下文，监控智能体记得上周基线，但事件无界增长，上下文管理必需。临时会话每个滴答都新鲜，当每个滴答独立时正确。给无状态作业选持久等于白白买无界存储，给需要记忆的作业选临时等于每个滴答扔掉记忆。

一个填满的窗口里什么得以存活

长跑循环会撞上上下文窗口，运行支架得回答两个自己不会回答的问题：什么被保留，谁决定。自动压实把较早的回合总结，让会话越过硬上限。失效模式是结构性的：总结丢细节，智能体对丢了什么毫无信号。Anthropic 的 cookbook 测出压实保留三个高层事实中三个，零个冷僻细节中零个 (Anthropic 2026)。

替代方案是外置化。智能体把想保留的写到文件（progress.md、plan.md），压实后重新加载。这用智能体对自身未来需求的盲目换掉总结的盲目。两者都不是机械的，下面争议框会讲。

「直接用更大的窗口」是诱人的第三选项，它挪走故障而不是消除它。更大的上下文窗口降低压实频率但不消除衰退。即便检索完美，准确率也随输入长度增长而下降 (Du et al. 2025)，同样的衰退在各种现实检索设定下都出现 (Hong et al. 2025)。「把一切都塞进去」只是把故障从「上下文溢出」挪成「上下文已满而模型悄悄变差」。

争议所在长会话的上下文管理能否做成机械的，尚无定论，证据说现在还不能。Lindenbauer 等表明，用占位符遮蔽旧工具输出，在五种设定中的四种以最低成本与 LLM 总结打平解决率，但总结会导致轨迹延长，智能体比最优多坚持 13 到 15%，因为总结遮蔽了该告诉它们停下的失败信号 [@lindenbauer2025complexity]。有帮助的压实工作比如学习式上下文压实 [@acon2025context]，仍把核心问题悬而未决。更大的窗口也不解决问题，因为即便最简条件和完美检索下，准确率也随长度衰退 [@du2025context]。

长会话质量倚赖三件运行时无法机械保证的事：模型被要求时写好总结，模型重新加载时解读总结，运行时强制外置化模式而不寄望于智能体自己维持。运行时能在对时刻触发压实并重新加载对的文件。它无法让总结真。

模型如何得知一个工具的存在

分发是工具怎么跑，注册表是模型怎么得知工具存在。静态扁平列表把每个工具都塞进系统提示，大约 30 到 50 个工具就用尽了，因为函数调用准确率随目录增长而下降，无关工具在场时鲁棒性尤其受损 (Yan et al. 2025)。过了这点，运行时就需要每轮选择。

安全侧的故障最尖锐：目录层一段恶意工具描述能通过系统提示把指令注入模型，完全绕过用户提示（Invariant Labs 的 mcp-injection-experiments）。注册表不是中立查找表，这就是为什么目录准入是交给 第 34 章 的信任决定。注册表准入到目录的东西，就是准入到模型指令的东西。

选择演化成阶梯，每级抬高目录天花板并添加运行时随后要掌管的代价。静态扁平列表让位给动态工具 RAG，后者嵌入工具模式并按每轮检索 top-k 相关项，扩展到数千个工具，代价是有自身错误的检索层。分层命名空间带挂载卸载，按阶段展示修剪子集，理解问题时只读工具、修复时写工具，要求运行时跟踪阶段。模型驱动发现给模型 list_available_tools 让它自己问，抬高天花板但让发现质量成为运行时不拥有的模型能力的函数。图 23.4 把四级摆在各自买来的天花板和代价旁边。

一个有状态的工具拖在身后的东西

工具沿有状态性轴折入设计。无状态工具（网页抓取、给定沙箱 ID 的沙箱执行）不持运行支架侧的状态，可平凡扩展。有状态连接工具（MCP、gRPC 流）在运行支架为会话握着的连接里携带协商好的能力与游标，把它们与无状态调用用同一机制分发会误处理一类或另一类。最难的变体是把两者混的单个逻辑操作，因为部分失败空间是两者的乘积。

有状态工具传输是本章最清晰的谱系。最简单的设计按副本把连接存内存，以 (session_id, server_url) 为键，惰性打开。一直管用直到平台横向扩展，这时有状态性和负载均衡器打起来。MCP 2026 路线图把有状态会话点名为首要扩展瓶颈 (Protocol 2026)。具体故障是重连风暴。一副本握着 N 个会话（每会话各连 M 个服务器）死掉时，恢复是对幸存基础设施的 N 乘 M 次同时重连，每次重新协商能力并丢游标状态。

机制决定了缓解：会话亲和把连接保在一副本上，带抖动的重连退避把羊群去同步，可恢复流让重连廉价。MCP 规范顺着这条曲线走，弃用 HTTP+SSE 转向 Streamable HTTP，重连时用 Mcp-Session-Id 加 Last-Event-ID 从游标重放而不重新开始 (Protocol 2025; Protocol 2025)。同一规范还加固连接池本身触不到的隐患：多个并发会话争刷新单次使用 OAuth 令牌时，输的递上已消费令牌失败，于是 2026 规范强制 RFC 8707 资源指示符，使令牌不能对错服务器兑现 (Campbell et al. 2020)。

多智能体组合有条平行弧线，OpenAI 实验性 Swarm 被 Agents SDK 取代，但组合本身属于 第 24 章，运行支架只掌管被组合智能体是共享还是隔离会话与沙箱状态。共享选择是自己的权衡，有被测的代价。共享会话与沙箱最廉价，代价是竞态与提示污染。完整沙箱隔离最多管道工最强隔离。Geng 和 Neubig 在 Commit0-Lite 上测出工作树隔离 59.1%，软指令级隔离 56.1%，软隔离在 PaperBench 上跌到单智能体基线下 (Geng and Neubig 2026)。指令级约束是劝告性的，真正隔离不依赖模型遵从。

为长夜加固

循环本身很小。围绕它的机制才是本章讲的，最后一部分集中在少数运维选择，这些决定了循环能否熬过无人值守的运行。

锁有两个来自锁定文献的坑。Redis 锁需要栅栏令牌才能在网络分区下安全（Kleppmann 对 Redlock 的批评）(Kleppmann 2016)。PgBouncer 事务池化下，pg_advisory_lock 在连接归还到池时释放，期望会话级锁的调用方必须用 pg_advisory_xact_lock 或专用会话池，否则锁会在滴答执行到一半时蒸发。

加在每个会话上、不论触发方式的挂钟超时，是即便词元计数出错或滞后也成立的那个上限，因为挂钟时间是运行支架能本地测、无需信任下游计量表的量。它为何承重的证据很刺眼：一条 LangChain A2A 流水线在两个智能体间循环十一天，产生大约 47000 美元账单，两个都没预算上限 (Waxell 2025)。一次 Claude Code 递归在五小时里消耗大约 16.7 亿词元 (anthropics/claude-code 2025)。

准入控制属于运行支架层。调用 Kubernetes API 的会话创建请求沙箱而不是创建一个，危险的故障不是拒绝而是挂起：Pod 处于 Pending，到客户端的流永远不开始，没有错误浮现，因为什么都没出错。在向客户端许诺会话前检查容量，把缓慢无声的「什么都没有」变成客户端可据以重试的快速清晰「不行」。

其余控制遵循同样机械推理。抖动防止许多智能体共享调度时的羊群效应。断路器在 N 次连续失败后停用智能体，使它不能无限烧词元。2025 年 12 月的 AWS Cost Explorer 故障在事故报告里被关联到一个以宽泛权限行事、没有断路器的自主智能体 (Singh 2025)。启动时的自愈会重放那些结束从未被记录的滴答，之所以安全只因上面的幂等键吸收了重放。

沙箱化本身从运行支架的座位上看很薄：为正确性掌管工作树隔离，为容量掌管准入控制，其余归沙箱原语掌管。

收束的透镜是能力、效率与信任。运行支架买来能力，让循环在有状态工具与被组合智能体间全速跑。为效率付费，靠上下文管理与准入控制，让失控不至于烧光预算。赢得信任只在一处：人对运行中智能体的权威，恰好等于运行时暂停它的能力，那是从一开始就被设计进去、否则就没有的性质。

约束箭头运行支架对评估分数的影响不亚于模型本身。基准数字是模型在运行支架内部跑产生的。Berkeley RDI 表明顶尖智能体基准可以通过利用运行支架本身作弊，从 `git log` 里读答案或对评分器做奖励黑客，多个基准在智能体根本没解任务的情况下就逼近 100% [@rdi2025trustworthy]。漏洞住在运行支架里而非任务里。后果向上触及 @sec-benchmarks 与 @sec-evaluating-agents。

一个分数是模型与其周围脚手架的联合性质，运行支架的改动就是测量的改动。评估套件必须加固运行支架而不只是留出私有答案册。留出集防的是记住答案，对一个读评分器的智能体毫无办法。
