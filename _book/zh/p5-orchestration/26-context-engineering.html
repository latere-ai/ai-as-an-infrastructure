上下文工程

前沿模型不直接作用于世界，它作用于自己的上下文窗口。窗口是一段有界的词元序列，它在单次前向传播里能看到的全部。模型在生成时用到的一切、指令、检索文档、对话历史、工具返回、都是由模型外部的什么东西装到这个窗口里的。

这个工作 2025 年改名成了上下文工程，取代「提示工程」。但改名后面有个顽固的事实：窗口越大，问题还是不会消失，只是挪了个地方。

这章就是在讲这个事实怎么玩的。从窗口为什么不如想象那么有用，到还剩什么办法，再到跑着的智能体怎么组装上下文、这套组装在哪儿崩溃。

窗口是唯一的通道

上下文窗口是固定而稀缺的资源，也是模型感知任务的唯一通道。这句话得停下来好好想想。

窗口大小是定的，里面每个词元都在争同一片空间。系统提示、工具定义、检索文档、长对话历史，全从一份预算里取。超了就得丢掉一些、摘要一些、或临时检索，每种选择都决定模型最后能答什么。没有第二条路。模型没看到就不知道。

大概会想，窗口更大应该解决这个。下面讲的就是为什么没有。

为何更大的窗口帮不上忙

模型对窗口里的词元不是均匀注意的。即便信息明确就在那儿，模型也只在开头和结尾注意得可靠，中间最弱。Liu 等叫它 lost-in-the-middle 效应 (Liu et al. 2023)，他们在多文档问答和键值检索上测到典型的 U 形曲线：所需事实在开头或结尾准确率最高，到中间就掉，有时甚至不查都强。更大的窗口没法改这个，只是把死区拉长了。

图 26.1 就是这个结果。两端可靠，中间衰减。所以事实摆在窗口的哪儿，不只是有没有在，决定模型是否真会用它。

改变事实位置，看回忆率怎么动。下面模拟 U 形，用蒙特卡洛把一个事实分别放开头、中间、随机位置，比命中率。

import numpy as np
import matplotlib.pyplot as plt

rng = np.random.default_rng(0)
pos = np.linspace(0, 1, 41)              # position in the window, 0=head 1=tail
recall = 0.45 + 0.5 * (2 * pos - 1) ** 2 # U-shape: high at edges, low in middle

def hit_rate(p, trials=20000):
    prob = np.interp(p, pos, recall)
    return rng.random(trials) < prob

for name, p in [("head", 0.0), ("middle", 0.5), ("random", None)]:
    where = rng.random(20000) if p is None else p
    print(f"{name:7s} recall = {hit_rate(where).mean():.3f}")

plt.plot(pos, recall); plt.xlabel("position (head to tail)")
plt.ylabel("recall probability"); plt.title("lost in the middle"); plt.show()

根本问题不是「怎么全装进去」，是「装什么、怎么摆，才能让模型用」。这是预算和排列的问题，也是本章的核心。

杠杆：把上下文当作编程界面

模型权重推理时锁死的，剩下唯一的杠杆就是什么进窗口、放哪儿。设计思想是把窗口当一个受管的缓冲，不是提示。

这根杠杆存在，因为上下文学习。Brown 等用 GPT-3 证明，足够大的自回归模型能从上下文里的例子学会做任务，根本不需要更新权重 (Brown et al. 2020)。他们按例子数分三种：zero-shot 只有指令，one-shot 一个例子，few-shot 少量例子（通常十到百个）放得进窗口。关键发现是：上下文本质上就是编程界面。一次会话里改变输入就改变行为，代价只是那些例子的词元。

上下文是编程界面后，对它的装配成了值得工程化的活儿。领域综述把它列成独立学问 (Mei et al. 2025)。Andrej Karpathy 2025 年中主张改名为上下文工程，理由是「prompt」让人想短指令，实际应用干的是「用对的信息为每步填充窗口，精细的艺术和科学」(Karpathy 2025)。Tobi Lutke 同周也从应用角度说了类似话：上下文工程是「为任务给足上下文让 LLM 能解，那艺术」(Lütke 2025)。改名不只是换词。它改了工作的单位，从人手写的字符串，变成系统组装的流水线：系统提示、检索文档、对话历史、提炼记忆、工具输出，为跑着的智能体每一步而组织。

三个动作：预算、摆放、压缩

窗口有限、模型少用中间，直接推出三个设计动作。

预算。 把窗口当按流量计费的资源。先扣固定开销（系统提示和工具定义），剩下的分给历史、检索和输出空间。检索（第 25 章）之所以必要，就是不是所有东西都要同时在窗口里，语料库在外，每次查询只拉进相关的片。

摆放。 中间是弱位置，顺序很关键。指令和最有价值的证据，要放在注意力可靠的地方，也就是靠近边界，不要埋在一大堆无差别的内容里。lost-in-the-middle 是模型的性质，它对上面的设计层定了个约束。

压缩而非累积。 对话或轨迹会无限增长，窗口不会。旧回合压缩成提炼状态，工具输出返回前过滤，持久事实写进外部记忆（第 22 章），用时再取，不是原样推着走。

约束箭头上下文预算不是美学选择，是被下层的词元成本硬性规定的。窗口里的每个词元都必须住在 KV 缓存里

并被注意到，第 16 章 的服务问题和 第 17 章 的缓存调度都表明，这个成本随上下文长度增长，内存和算力都是。更长的窗口不是你随便填满的免费空间。正是这个每词元 的服务成本，让紧凑、排好序的上下文成为对的设计，即使在技术上窗口还能更大。

从一条字符串到一条流水线

这三个动作不是一开始就有的。从单条字符串演进到受管流水线，看这个历程能明白每个动作为什么要。

第一个时代是提示工程。上下文学习确立后，从业者学会靠措辞从模型套行为：精心写指令、加几个做好的例子、末尾加「let's think step by step」引导思维链（第 13 章）。产物就是提示模板，手工写决定好坏。

瓶颈随着应用变大而露出来。手写字符串装不下大知识库、长对话、模型工具调用的输出。检索增强生成（第 25 章）解决知识库问题，查询时取相关段。智能体运行框架（第 23 章、第 21 章）解决行动问题，让模型调工具、结果送回窗口。两个都把上下文从固定字符串变成运行时从多源组装的东西。于是「提示工程」对这工作就太窄了。2025 年改名上下文工程，是领域为早就干的事起名：Karpathy 和 Lutke 贴了标签，但预算、检索、排序、压缩的活儿早在做了。

递归：为工具本身做预算

工具带来了集成难题和协议，这协议又把预算问题弹回来了。

2024 年末之前，每个应用用定制胶水把模型接各数据源，N 乘 M 的问题。Anthropic 2024 年 11 月发布模型上下文协议（MCP）作为标准接线方案 (Anthropic 2024)：模型只用一种协议，任何 MCP 服务器（文件系统、数据库、问题追踪器）都通过它暴露工具和数据。MCP 标准化了外部上下文和能力进窗口的方式。图 26.2 对比两种接：一个是各模型直接接各数据源的定制网格，一个是两边各用协议一遍的中心。

但这协议随之在上层暴露新预算问题。智能体连上几十个 MCP 服务器，工具定义本身就填满窗口，还没读请求呢。2025 年 11 月 Anthropic 提代码执行加 MCP 作解法 (Anthropic 2025)：不预加载每个工具定义，把 MCP 服务器当代码 API，模型通过写代码发现和调用，只加载任务需要的定义，结果返回前在执行环境过滤。他们例子把工作流从约 150,000 个词元（定义加中间结果）降到约 2,000 个，减了 98.7%。这就是本章讲的教训：约束就是上下文预算，设计要守住它。

平衡在哪里咬人

上下文工程是一组平衡，各有各的拐点。

  • few-shot 与 zero-shot。 示范提高可靠性，但花词元，每个示范词元都是从检索、历史或输出里挪出来的。指令微调模型越来越强，平衡点在移：过去需要几个例子的任务现在能 zero-shot 做，例子只在钉格式或指令无法简洁表达的情况时值那成本。
  • 更多上下文与更好的上下文。 窗口塞满看似相关的一切，简单但常常是错。会抬高调用成本，把高价值证据推进 lost-in-the-middle 死区，模型就少用它。小、精选、排好序的上下文，通常胜过大而杂乱的。
  • 静态提示与装配流水线。 固定模板简单好调试，推理成本低。按步检索、排序、摘要、重排的流水线更能干，但引入各自会失效的活动部件：检索失手污染上下文，摘要出错丢掉下一步需要的事实。
  • 工具广度与词元成本。 接许多工具原则上让智能体更能干，但把全部工具定义预先加载，就在工作开始前花掉预算。渐进加载，也就是像代码执行加 MCP 那样按需装定义，代价是多一个发现步骤、更复杂的运行时，但把预算要回来。
争议所在现在还有几处意见不同。一个是：长上下文模型是否让精选上下文变得多余。一派说，窗口长到几十万

乃至上百万词元，干脆全部加载、让注意力自己梳理，检索和排序就成了过时的权宜。另一派指向 lost-in-the-middle 和每词元成本：模型会少用中间，窗口按调用计费，所以无论窗口多大，选和摆仍然更赢。第二个争论是「上下文工程」是不是真给一门新学问命名，还是给提示工程改个说法。 Karpathy 直接说不是生造术语，是在反对「prompt」造成的过度简化。第三个关乎 MCP 最初设计： Anthropic 自己后来的代码执行表明，把全部工具定义预先加载是个坏默认，怎么把工具暴露给模型还没定论。

构建一次上下文，以及它如何崩坏

实际中，一次模型调用的上下文是构建的，不是写的。一个有预算意识的装配器就够了：

def build_context(task, history, tools, retriever, window):
    budget = window - reserve_for_output(window)
    parts = []
    parts.append(system_prompt(task))          # fixed, goes first
    parts.append(tool_manifest(tools))         # load on demand if large
    evidence = retriever.search(task.query)    # only the relevant slice
    parts.append(rank_and_trim(evidence, budget))
    parts.append(summarize_old(history, budget))  # compress, do not accumulate
    return order_for_attention(parts)          # high-value near boundaries

图 26.3 把这装配器画成数据流。许多来源流入有预算的缓冲：固定开销先扣，检索只把语料相关部分调进，历史压缩不是一直推，最后排序步骤把最有价值部分放边界，也就是 图 26.1 说模型会实际读的地方。

这个草图的三个性质贯穿全章论点。输出余量要先从最上面扣，不然填满的上下文会让模型没地方答。检索返回一片段，不是全库，知识库在窗口外，只有相关部分被拉进。order_for_attention 不是摆样子：它把指令和最强证据放在 lost-in-the-middle 说的、模型真会读的地方。

失效模式值得一一说，因为各自在不同地方出问题。上下文溢出无声截断，丢掉末尾的东西，常常正好是下一轮需要的历史。lost-in-the-middle 的衰减在绿色构建里看不到：事实在那儿，模型就是不用，只能改位置、看分数移动才能看出来。检索中毒是一段错段落被当成证据。工具定义膨胀在智能体开始前就把预算花完，这正是代码执行加 MCP 要解决的。这些都是预算或排列的失败，所以预算和排列，不是措辞，才是这门学问的内核。
