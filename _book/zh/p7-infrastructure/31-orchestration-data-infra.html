第七部分 · 基础设施与系统 · 第 31 章

编排与数据基础设施

一次前沿运行让数千张加速器步调一致地连续工作数周，而它底下的硬件按自己的节奏失效。计算工作，即矩阵乘法与集合通信，是看起来困难的那部分，但它不是决定运行能否完成的那部分。在数千个节点 连续运行数周的规模上，故障是稳态，而非例外：一张 GPU 掉出总线、一块网卡抖动、一台主机 OOM，而由于集合通信是成组调度（gang-scheduled）的，单个失效的参与者就会拖停整个作业。本章负责的， 是在它底下的硬件不断损坏之时，让这样一次运行保持存活且诚实的运维层。

读完本章，你会明白检查点频率为什么是一个经济决策，数据采样器的状态为什么必须进检查点，以及一个失效节点为什么能把一整天都浪费掉。这一层所运行的加速器与互连，第 30 章 会专门展开；它所检查点、所喂养的并行布局，第 8 章 会进一步深入。这两样本章都不负责。本章负责的，是步与步之间、以及跨故障时发生的那些事。

把故障当成稳态，会落出三条义务，本章其余部分就围绕它们组织。第一，运行要可恢复，节点死了就从近期保存的状态继续，而不是从头再来。第二，数据加载层要让加速器被喂饱，按它们消耗词元的速率交付，而且可复现地交付。第三，运行要足够可观测，故障要从遥测里被捉住，而不是好几天后才从一条悄悄走偏的损失曲线里发现。三者都是运维的活儿，都不光鲜，也都决定了那笔昂贵的计算到底值不值。下面逐个来谈，最后再回到撑着这三者的调度器和成本旋钮。

熬过故障：检查点与重启

针对故障的核心机制是检查点：周期性地序列化模型参数、优化器状态、学习率调度位置与数据采样器状态，使运行能从那份快照重建。优化器状态主导着写入量，因为 AdamW 为每个参数携带两个矩估计， 这正是 第 8 章 沿数据并行组切分的那份状态 (Rajbhandari et al. 2019)。

朴素的检查点会停掉每个 rank，写到存储，再继续，把整个写入延迟压在关键路径上。这是最初的明显设计：暂停，把一切写到共享文件系统，恢复。模型还装得轻松、集群也还小的时候，这么做尚能忍受，可它扩展性很差，因为要写的状态和故障率都随运行增长，于是同步写入从微不足道的零头变成了显眼的开销。有两个想法能把写入挪出关键路径。异步检查点把张量先抄到主机内存或暂存缓冲区，让训练继续，由后台写入器慢慢把它们排到存储。CheckFreq 把这个修法讲得最干净：它把快照和写入流水化，开销低到短频率也负担得起，于是检查点从一桩粗放又昂贵的事件变成了家常便饭 (Mohan et al. 2021)。切分或分布式检查点则让每个 rank 只并行地写自己那份状态，于是写入时间随单个 rank 的状态扩展，而不是随总状态。这一步沿用了完全切分数据并行的布局，那里的状态本就已经分散在整个集群上 (Zhao et al. 2023)。

频率是一个经济决策

频率本身是个优化问题，不是常数。检查点太稀疏，一次故障就会回滚大段工作；检查点太频繁，写入本身又会吃掉存储带宽、偷走时间。最优值在每次故障的期望损失工作量与一次写入的成本之间取平衡，这也是为什么平均故障间隔更短的集群想要更短的频率。一个有用的初步估算：若故障以速率 λ\lambdaλ 到来、一次检查点的写入成本为 CCC，那么最小化总浪费时间的间隔 TTT 大致按 T≈2C/λT \approx \sqrt{2C/\lambda}T≈2C/λ​ 变化，也就是保存成本与重放成本之间那个熟悉的平方根权衡。频繁的检查点缩小了每次故障损失的工作量，却要吃存储带宽、还可能拖停运行；稀疏的检查点写起来便宜，故障一旦命中却代价高昂。异步与切分检查点正是让短频率一开始就负担得起的东西，而最优值取决于集群 MTBF 和写入成本，而非某个固定的步数。

挑一个写入成本和一个故障率，看那个数值最优值如何从平方根公式里落出，停在 U 形浪费曲线的谷底。

import numpy as np
import matplotlib.pyplot as plt

C = 30.0          # checkpoint write cost, seconds
mtbf = 6 * 3600   # mean time between failures, seconds
lam = 1.0 / mtbf  # failure rate

T = np.linspace(60, 36000, 2000)        # checkpoint interval, seconds
waste = C / T + lam * T / 2             # write overhead + expected replay, per unit time
T_star_numeric = T[np.argmin(waste)]
T_star_formula = np.sqrt(2 * C / lam)
print("numeric optimum T*:", round(T_star_numeric), "s")
print("formula sqrt(2C/lambda):", round(T_star_formula), "s")

plt.plot(T / 60, waste, label="total waste rate")
plt.axvline(T_star_formula / 60, color="C1", ls="--", label="T* = sqrt(2C/lambda)")
plt.xlabel("checkpoint interval T (minutes)")
plt.ylabel("wasted time fraction")
plt.title("U-shaped waste versus cadence")
plt.legend(); plt.grid(alpha=0.3); plt.show()
约束箭头检查点频率是被下层定下的。@sec-accelerators-networking 里加速器与互连的平均故障间隔，决定了运行会多频繁地被掀翻，而正是这个故障率，而非模型或训练配方的任何属性，钉死了经济的保存间隔。硬件越不稳的集群必须越频繁地检查点，这又抬高了存储带宽需求、压低了有效吞吐。一个看起来像调优旋钮的运维选择，实则由它底下那层的可靠性设定。

恢复，以及那些不会崩溃的故障

恢复是另一半。弹性重启检测到失效节点，把它隔离出集合通信，再从最近的检查点恢复幸存者，理想情况下落到预热好的备用容量上，这样作业既不必等人、也不必等失效主机回来。更棘手的是那些不会干净崩溃的故障：跑得慢的掉队节点会把每次集合通信都拖到它的步调，而静默数据损坏让运行继续跑、却产出微妙错误的数字，任何检查点都救不了你，因为检查点会忠实地把损坏一并记录下来。

图 31.1 里的分叉就是设计点：一次干净的崩溃走快路，检测、隔离、在预热备用节点上恢复；而那些从不触发崩溃检测器的故障，要么得靠可观测性捕获，要么干脆已无从恢复。

检查点存于何处，以及仍有争议之处

把检查点写到存储底座持久且能活过集群级事件，但慢；暂存在主机内存或跨对等节点复制则写得快、恢复也快，可一旦集群同时宕掉足够多的部分就会丢失。这个选择是在持久性和检查点成本之间做权衡，多数运行会把一个频繁的廉价层和一个偶尔的持久层组合起来。养着热备用节点能让一次弹性重启在数秒而非数分钟内恢复，但那些节点是花了钱的，在故障用上它们之前一直闲着：这份预留是保险，保费就是利用率。

争议所在前沿规模上如何做检查点尚无定论。一派坚持把持久写入留在存储底座，再用异步、切分的快照把它做便宜。另一派则认为存储太慢，这个规模上没法做到足够频繁的检查点，答案在内存内或对等复制的检查点：把近期状态留在主机内存、或切分到冗余节点上，于是一次重启能在数秒内从 RAM 恢复，只在面对相关性故障时才退回持久存储。两者意味着不同的成本结构、对相关性故障也有不同的容忍度，各家前沿栈之间并没有一个尘埃落定的默认选择。@fig-orchestration-checkpoint-tiers 把两派沿着区分它们的那些轴并排铺开。

喂养加速器：数据层

第二根支柱让加速器保持被喂饱。语料被分词成许多分片，存在一个高吞吐的存储底座上，那是一套并行文件系统或 NVMe-over-Fabrics 层，规模大到足以按每秒数 TB 的速度供应整个集群，前面通常还垫着一层本地 NVMe 缓存。每个 rank 读自己分到的分片，在当前批训练时预取并流水化下一批，让加速器从不等 I/O；一次全局打乱则避免单个分片的局部相关性带偏某一步。加载顺序遵守 第 4 章 给出的混合权重，那决定了每个数据源被抽到的频次。

这一层从映射式数据集演化而来。映射式做法把一份装在内存里的语料拿来索引，后来变成了流式的、分片的流水线，从不具体化整个语料，因为一份数万亿词元的语料既装不下，也没法廉价地随机索引。

可复现性把数据层系回检查点

把数据层系回检查点的那个属性，是可复现性。一次恢复必须续上运行在没出故障时本会走的那条确切的数据顺序，这意味着采样器与打乱状态，即排列里的位置、轮次、各数据源的抽取计数器，都是检查点的一部分，而不是重启时新算出来的，正如 图 31.3 所示。没有它，恢复会重喂或漏喂数据，悄悄破坏混合契约。

可复现性这一需求是随规模到来的。小规模上，非确定性的恢复只是个麻烦；可到了前沿规模，恢复频繁、混合契约又是承重的，检查点保存采样器状态就成了没有商量余地的事。它并非免费：确切的数据顺序可复现性要付出确定性开销，因为采样器状态必须进检查点、打乱也必须可重放，这就约束了你能为 I/O 效率把顺序重排得多激进。放弃它能换来一些吞吐，却也丢掉了干净恢复、以及把一处损失断点归因到其成因的能力。

知道运行是否健康：可观测性

第三根支柱的设计源于一个事实：单看损失曲线，无法告诉你系统的活儿做得对不对。运行可能很慢、卡在通信上、或悄悄退化，而损失仍在下降。所以这一层要给步本身装上探针：每步墙钟时间及其拆分、暴露的通信对重叠的通信、以及能足够早捕获发散或尖峰、好让你来得及动手的梯度范数与损失遥测。诊断的单位是一条每步的时间线或剖面，而不是瞟一眼损失。

这正是那些逃过崩溃检测器的故障被抓住的地方。掉队节点在每步拆分里现形为一个慢的 rank；发散则在损失明显转向之前先以一处梯度范数尖峰现形。静默数据损坏是连好的可观测性也难对付的那一类，因为数字是错的、却并不异常，这也是它落在 图 31.1 中无法恢复那一端的原因。

把三者系在一起：调度器与成本旋钮

成本与调度坐在这三根支柱底下。由于集合通信是成组调度的，作业要么同时拿到全部节点、要么一个节点都推进不了，所以调度器预留下整组，并保持备用容量预热，好在不必整体重启的情况下吸收一次故障。检查点频率、备用节点供给、以及存储底座带宽，是几个运维成本旋钮，它们直接同运行的吞吐相抵。每根支柱都已经花掉了其中一个旋钮：频率换来可恢复性，备用容量换来快速重启，存储带宽既换来一个持久检查点层、也换来一个被喂饱的数据层。调度器，是让一次预留同时把这一切都攥住的东西。

这一层如何被组装

实际中，运维层是组装出来的，不是整套买来的。模型与优化器的切分来自并行框架，但检查点、数据、可观测性这几层往往是定制的，因为它们的频率、切分和可恢复性必须贴合某次运行的确切布局。

这个规模的检查点不是一个文件。每个 rank 序列化自己那份参数与优化器状态，外加那些小却承重的标量：步数、学习率调度位置、以及数据采样器状态。契约的一个草图：

state = {
    "model_shard":     shard_of(model.parameters()),
    "optim_shard":     shard_of(optimizer.state),   # dominant term
    "step":            step,
    "lr_schedule_pos": scheduler.position(),
    "sampler_state":   loader.sampler.state_dict(),  # makes resume reproducible
}
async_write(state, path_for(rank, step))             # off the critical path

值得点名的两种失效模式都来得晚、也来得悄无声息。一次没有近期检查点、也没有快速检测的节点故障，会把运行回滚到上一次保存，把中间的间隔当成纯粹的浪费烧掉，这就是为什么检测、隔离和一个近期检查点是一个系统，而非三个。一次重启时的非可复现数据顺序，源于一个没进检查点的采样器状态，它会重喂或漏喂数据，破坏 第 4 章 的混合契约；它在每次恢复时以一处无从解释的损失断点现形，而当它其实是个运维 bug 时，很容易被误读成训练配方的问题。两者都被这一层装上的可观测性捕获，也都靠把采样器状态和恢复路径当成检查点的头等组成部分来预防。
